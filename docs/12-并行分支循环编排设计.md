## 项目启动与 submit 调用现状

当前生产源码没有 main、SpringBootApplication、组装 AgentOrchestrator 的工厂/Bean 或调用 submit 的业务入口，因此还不能直接启动完整 Agent。编译通过表示组件代码可编译，不等于应用启动已完成。

`AgentOrchestrator.submit(Request)` 是一个任务的提交入口；调用方须先准备模型解析器、工具注册表、仓储/嵌入、匹配/门禁/验收策略、执行图、工作池和计时器，构造编排器，再把用户目标封装成 Request 调用 submit。返回的 Handle.result 是异步结果。`AgentCaller.call(Request)` 仍是仅调用一次模型的入口，调用它不会自动进入外层循环。

```text
应用 main / Spring Boot 启动类       尚未实现
  → 创建并装配 AgentOrchestrator    尚未实现正式装配
  → 接收用户输入                   尚未实现
  → orchestrator.submit(request)   已实现
      → 本文下面的检索、模型和执行流程
```

目前直接创建编排器并调用 submit 的样例仅在 checks/java 的 AgentOrchestratorTest.Harness，使用替身依赖，用于验证组件。用户要求后，全部原 src/test 已迁到独立 checks 目录；不能把检查 main/Harness 称为正式启动入口。本轮仅复核并迁移检查资料，没有新增假的生产装配或用全部放行策略冒充真实门禁。

## 1. 实际调用链

```text
AgentOrchestrator.submit(Request)
  → 根入口 searchAtEntry，只调用一次
  → 整条匹配：检查资格、执行固化、验收、返回
  → 未匹配：runDecisionRound（执行一轮模型决策）
      → AgentCallerPlanner.decide(context)
          → AgentCaller.call(request, scopedTools)，CALL_ONLY
          → 一次 ChatModel.call
          → 解析结构化 toolCalls，生成 Decision
      → PLAN：每次都 searchAfterPlanning，再执行计划
          → 命中固化步骤：直接执行固定版本
          → TOOL：SpringToolExecutor → ToolCallback
          → TASK：递归 task → runDecisionRound，不重复入口检索
      → 计划反馈进入下一次单次调用
      → COMPLETE：验收最终输出并返回
      → NEEDS_INPUT：返回待补充信息
```

循环由 AgentOrchestrator 驱动；AgentCaller 始终只调用一次模型。计划由模型提出，代码负责校验、调度和保存执行事实。模型不操作 Java 线程。

## 2. 类型、工具调用与入参

模型可见两个控制工具，模型响应必须恰好包含一个工具请求：

| 原生工具名 | arguments | 解析结果 |
| --- | --- | --- |
| submit_plan | TaskPlan 的 JSON | DecisionKind.PLAN |
| finish_task | kind: COMPLETE / NEEDS_INPUT 和 output | 对应结束决策 |

判断工具请求来自 Spring AI 的 AssistantMessage.getToolCalls()，使用请求中的 id、name 和 arguments，不从自然语言里寻找“我要调用工具”。AgentCaller 在两种模式下均校验调用 ID 非空、不重复，以及工具名属于本轮允许集合。

编排适配器用 JSON Schema 告诉模型入参结构，再用 Jackson 转成 TaskPlan。类型决定代码分支，类型本身不理解用户意图。当前实现已用 switch(decision.kind()) 明确分发 PLAN、COMPLETE、NEEDS_INPUT；PLAN 交给 executeModelPlan，步骤再用 switch(step.kind()) 区分 TOOL/TASK。没有固定的“规划 → 执行模型 → 总结模型”三次调用。工具执行通常不调模型，总结可以由后续模型返回 finish_task.output。

原 loop 方法已改名 runDecisionRound，意思是“执行一轮决策”。switch 只负责选择本轮分支，轮次推进仍由计划完成后的异步回调再次调用 runDecisionRound。不能简单删除轮次接续，否则只会执行一次计划；也不应在工作线程内同步等待整棵子任务树。submit → task → runDecisionRound → executeModelPlan → executePlan 是建议阅读顺序；TOOL 动作的代码单独放在 executeToolStep。

## 固定值为什么存在

本轮按用户要求给新增核心代码的逻辑语句逐行补中文注释、展开压缩分支；字段注释仍放声明上方。保留以下区别，避免把所有字符串都当作业务魔法值：

| 固定值 | 当前表示及原因 |
| --- | --- |
| TASK、MODEL、TOOL、SPAWNED、RUNNING 等链路标签 | 改用 ExecutionTraceStore 的 NodeKind、EdgeKind、NodeStatus 枚举，防止任意拼写 |
| submit_plan、finish_task | 提取为 AgentCallerPlanner 的工具名常量，是发给模型的工具协议名称 |
| $input、$entry、$plan | 提取为 TaskPlan/CapabilityLookup 的保留字常量，分别指任务输入、入口查询、整条计划查询 |
| 50ms | SpringToolExecutor.LOCK_CANCEL_CHECK_INTERVAL_MILLIS，是等锁期间检查取消的间隔，不是工具运行超时 |
| 16、0.75 | 内容缓存哈希表初始桶数/装载因子，已命名；真正缓存容量及 TTL 仍由构造器传入 |
| 1000 | MAX_CANDIDATES_PER_QUERY，是本地查询保护上限，不是 Qdrant 服务限制；实际候选数由 Config.limit 传入 |
| arguments、goal、status、result.points 等 | JSON/HTTP 协议字段，保留约定拼写并在代码旁解释；协议变更须同时修改读写方 |
| 0、1、~0、~1、HTTP 2xx | 分别涉及计数起点、版本规则、JSON Pointer 转义、HTTP 标准，按用途注释，不机械制造一批无意义常量 |

JSON Schema 和模型提示词是字符串内容，内部不能插入 Java 注释；在字符串定义上方解释用途，避免注释改变模型实际输入或破坏 JSON。

TaskPlan.Step 实际字段：id、goal、kind、toolName、arguments、dependsOn、bindings。kind 为 TOOL 或 TASK。例如模型调用 submit_plan 的参数：

```json
{
  "goal": "查询订单并生成报表",
  "steps": [
    {"id":"a","goal":"查询当天订单","kind":"TOOL","toolName":"queryOrders",
     "arguments":{"date":"2026-11-10"},"dependsOn":[],"bindings":{}},
    {"id":"b","goal":"根据订单生成报表","kind":"TOOL","toolName":"exportCsv",
     "arguments":{},"dependsOn":["a"],
     "bindings":{"rows":{"source":"a","pointer":"/rows"}}}
  ]
}
```

运行时先取 arguments 常量，再解析 bindings。source 为 $input 时读取本任务入参，其他 source 读取依赖步骤 Outcome.value；pointer 为 JSON Pointer。绑定结果覆盖同名常量。路径缺失或前驱不成功则不执行该步。解析后的 Map 序列化为 JSON，交给 ToolCallback.call(input, ToolContext)；工具自身负责业务参数校验。TaskPlan 校验不是完整 JSON Schema 校验器。

TASK 的入参传给递归子任务；运行身份和允许工具继承自运行时，模型不能任意指定父运行身份。

## 3. 检索与缓存时机

入口检索只发生在一次根 submit，使用用户目标。递归子任务和下一轮循环都不重复入口检索。

每次模型真正提交 PLAN 后，按该计划总体目标查询一次，再按每个步骤的 goal 分别查询数据库候选；不同轮使用不同 planRevision。COMPLETE 和 NEEDS_INPUT 不触发规划后检索。步骤查询同时携带原始 Step，供匹配策略核对工具名、类别和参数来源。

PlanMatches 保存本计划的整条/步骤匹配及不可变定义；CapabilityLookup 用有容量、TTL 的固定版本缓存减少重复内容加载。它不缓存搜索未命中，不用入口候选替代规划后检索。执行已有计划不会再次做语义搜索，但每次能力调用前通过 isAvailable 核对权威发布状态。详见[19](19-固化检索与缓存开发文档.md)。

匹配策略必须确认替换前后的输入、输出及副作用合同；不能仅靠同名工具或向量分数。当前组合执行输出为 stepId → {status,value,error}，没有自动输出字段映射器；不满足原步骤所需输出形状的能力不得替换。

## 4. 并发与失败

TaskPlan 校验步骤身份、依赖存在、数据绑定来源和 DAG 无环。就绪步骤提交给注入的 Executor；依赖通过 CompletableFuture.allOf(...).thenCompose(...) 唤醒。父任务不占线程同步等待子任务，因此一个工作线程也能完成递归任务。不同子任务可以同时调用模型；每个子任务自己的决策按轮顺序推进。同一计划收齐所有步骤结果后，再调用该父任务下一轮模型。

SpringToolExecutor.ResourceResolver 按本次参数解析实际资源，例如会话 ID、桌面、文件路径。相同资源经共享的条带锁串行执行，不同资源可并发；条带碰撞可能保守地串行。业务依赖来自模型/已有计划，资源互斥来自适配器掌握的真实资源，不使用注册工具时的固定“可并发”开关。跨任务需共用执行器实例才共享锁。

调用方管理工作池和计时器的生命周期、线程/队列容量；运行时另限制模型调用数、工具调用数、任务数、步骤数、每任务轮数、递归深度和总时限。当前没有按模型供应商分别限流。

Outcome.status 为 SUCCESS / FAILED / UNKNOWN / CANCELLED / NEEDS_INPUT。明确失败阻止依赖步骤，汇总后可让模型重新规划；UNKNOWN、取消或待补充直接结束自动推进。动作开始后的异常或验收异常保留为 UNKNOWN，不能自动假定副作用未发生。模型重规划仍可能提出重复动作；持久化幂等/副作用账本尚未实现。

## 5. 执行关系与装配

ExecutionTraceStore.snapshot(rootRunId) 提供不可变节点 Map、边列表和事件列表。记录 TASK、MODEL、SEARCH、STEP、UNIT、TOOL、GATE、VERIFY，以及父子、执行依赖和数据来源关系。它是进程内记录，不是已发布技能库；固化消费者合同见[13](13-执行链路记录开发文档.md)。

最小装配关系如下，变量均由调用方提供真实实现：

```java
var caller = new AgentCaller(modelResolver, callbacks);
var planner = new AgentCallerPlanner(caller);
var lookup = new CapabilityLookup(repository, matcher, cacheCapacity, cacheTtl);
var actions = new SpringToolExecutor(callbacks, resourceResolver, 256);
var traces = new ExecutionTraceStore(maxRuns, maxNodes, maxEvents);
var runtime = new AgentOrchestrator(planner, lookup, actions, checks,
        traces, workers, timer, limits);
var handle = runtime.submit(new AgentOrchestrator.Request(goal, arguments,
        modelRef, allowedToolNames));
// handle.result() 异步接收结果；handle.cancel().run() 请求停止后续调度。
// traces.snapshot(handle.rootRunId()) 供其他模块读取关系。
```

repository 已有 Qdrant HTTP 实现；仍需实际嵌入模型和明确来源的实体读取函数。Matcher、Checks.allow/verify 为必须注入的策略，生产代码没有默认全部放行实现。测试中的放行替身不代表真实门禁。
