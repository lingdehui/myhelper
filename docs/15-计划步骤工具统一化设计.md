# 计划-步骤-工具统一化设计（图化记忆结构）

> 状态：设计稿，待交叉验证
> 目标：用"统一对象 + 有序引用 + 无序禁用"的图结构，替换当前 Qdrant 扁平 Episode，使经验可细粒度复用、失败可结构化规避。

## 1. 背景与问题

当前经验闭环（Episode）存在三个结构性问题：

1. **扁平冗余**：完整 `toolCalls` 序列整体塞进 Qdrant payload。一个通用步骤被 N 个计划复用就要存 N 份，且无法单独复用"某一步"。
2. **复用粒度单一**：只能复用整个 Episode，不能复用其中的子步骤；匹配靠硬编码关键词，命中率低。
3. **失败经验与计划脱节**：失败教训存成独立文本（`FailurePatternNode`/`RuleNode`），不挂在具体计划/步骤上，无法在复用计划时自动规避。

## 2. 核心设计理念

1. **递归 Plan（一切皆 Plan）**：Plan 递归嵌套 Plan，最原子的 Plan 就是 `@Tool`。计划 = 大 Plan，步骤 = 子 Plan，工具 = 原子 Plan——三者本质同一，只是递归层级不同，都能被 AI 直接调用。
2. **分层注册**：`TOOL` / `MCP_TOOL` 注册为真正的 `@Tool`（可执行）；`PLAN_STEP` **不注册为 `@Tool`**，通过独立 `PlanLibrary` 查询接口提供"计划描述"（或注册为特殊工具但仅返回描述）。执行期才把 `PLAN_STEP` 展开为叶子 `TOOL` 执行，避免规划与执行耦合。
3. **稳定层区分**：只有 MCP 工具（robot-mcp 的 leftClick/typeText 等）是稳定基础设施，不可删；计划/步骤/工具是动态层，可删。
4. **正向有序引用**：计划按 1→2→3→4 顺序包含步骤，步骤可递归包含子步骤或工具。
5. **负向无序禁用**：失败经验直接固化为图上的"禁用边"，复用计划时自动跳过被禁用的步骤。
6. **失败原因独立对象**：网络、环境、原因、入参、分析、归类全部结构化，归类为"计划原因"的失败累计达阈值即触发禁用/删除。

## 3. 统一对象模型（Unit）

所有计划/步骤/工具都用一个统一对象表示，靠 `unitKind` 区分，格式完全一致；三者都是 `@Tool`，统一注册、统一调用、都带失败原因、都可删（MCP 工具除外，属稳定层不可删）。

| 字段 | 类型 | 说明 |
|---|---|---|
| `unitId` | String | 业务 UUID，对齐 Qdrant point id，两边互指 |
| `unitKind` | enum | `TOOL`（真正的原子工具，可删）/ `PLAN_STEP`（计划或步骤，组合单元，可删）/ `MCP_TOOL`（MCP 稳定工具，不可删） |
| `matchText` | String | 匹配语言字段，embedding **只对此字段生成向量**。**内容 = `goal + "。" + description`**（不含 notes） |
| `goal` | String | 描述字段：说清要达到什么目的 |
| `description` | String | 补充描述 |
| `notes` | List\<String\> | 注意点：注意事项、失败教训提示 |
| `params` | Map\<String,String\> | 入参签名（变量名→类型/默认值），**非必填**，被引用的步骤也可有自己的入参 |
| `outputSignature` | Map\<String,String\> | 输出签名（变量名→类型）：本 Unit 执行后产出的变量，供后续步骤引用 |
| `toolName` | String | `unitKind` 为 `TOOL` / `MCP_TOOL` 时指向的实际工具名 |
| `successCount` | int | 成功次数 |
| `failureCount` | int | 失败次数 |
| `stability` | double | 稳定度 = success/(success+failure)，**failure 只计 PLAN 原因**（环境原因不计入） |
| `failureCauses` | List\<引用\> | 失败原因引用列表（指向 FailureCause 对象） |

### 3.1 `unitKind` 在规划期 vs 执行期的角色

| 阶段 | `unitKind` 的用途 |
|---|---|
| **规划期**（doPlan 分类浏览） | 让 AI 区分三类：`PLAN_STEP`（可复用的历史计划/步骤，优先复用）、`TOOL`（原子工具，按需补充）、`MCP_TOOL`（稳定底座，始终可用） |
| **执行期**（executeWithTools 实际调用） | 系统据此决定调用方式：`TOOL` / `MCP_TOOL` → 原子，直接执行；`PLAN_STEP` → 组合，递归展开 `CONTAINS` 再逐层执行 |

**注册策略**（按 `unitKind` 区分）：
- `TOOL` / `MCP_TOOL` → 注册为真正的 `@Tool`，可执行；其中 `MCP_TOOL` 不删除。
- `PLAN_STEP` → **不注册为 `@Tool`**；通过独立 `PlanLibrary` 查询接口返回"计划描述"（或注册为特殊工具但仅返回描述）。执行期才把选中的 `PLAN_STEP` 递归展开为叶子 `TOOL` 执行，避免规划与执行耦合。

**示例（发消息计划）：**

```
Unit[PLAN_STEP] "发消息"            （顶层，无父级 = 计划）
  ├─ CONTAINS(1) → Unit[PLAN_STEP] "打开微信"   params:{app:"微信"}
  │                 ├─ CONTAINS(1) → Unit[TOOL] launchApp
  │                 └─ CONTAINS(2) → Unit[TOOL] findFriend
  └─ CONTAINS(2) → Unit[PLAN_STEP] "输入并发送" params:{text:"$message"}
                    └─ CONTAINS(1) → Unit[TOOL] typeText
```

## 4. 图结构

### 4.1 节点

| 节点 | 说明 |
|---|---|
| `Unit` | 统一节点，`unitKind` 区分 `TOOL` / `PLAN_STEP` / `MCP_TOOL` |
| `FailureCause` | 失败原因独立对象（见 §5） |

### 4.2 关系

| 关系 | 方向 | 是否有序 | 属性 |
|---|---|---|---|
| `CONTAINS` | Unit → Unit | **有序**（1、2、3、4） | `order`（int） |
| `DISABLES` | Unit → Unit | **无序** | `reason`、`failCount`、`condition` |
| `FALLBACK` | Unit → Unit | **无序** | `priority`（可选） |

- `CONTAINS` 表达"包含"：Plan→Step、Step→子Step、Step→Tool，按 `order` 顺序执行。
- `DISABLES` 表达"禁用"：失败经验总结出的规避关系，复用计划时直接跳过被禁用的目标。**挂在所有层**（Plan→Step、Step→子Step、Step→Tool），但**不挂在 MCP 工具上**（MCP 工具稳定，不参与禁用）。
- `FALLBACK` 表达"降级替代"：此单元失败/被禁用时，改用目标单元（"这个步骤不行，换另一个"）。

## 5. 失败原因对象（FailureCause）

| 字段 | 类型 | 说明 |
|---|---|---|
| `causeId` | String | UUID |
| `network` | String | 网络情况快照 |
| `environment` | String | 环境情况快照（如"屏幕被锁"、"无窗口"） |
| `reason` | String | 失败原因描述 |
| `inputArgs` | String | 失败时的入参快照 |
| `analysis` | String | AI 分析结论 |
| `category` | enum | `PLAN`（计划原因）/ `ENVIRONMENT`（环境原因） |
| `timestamp` | long | 发生时间 |

**归类规则**：
- `PLAN`：计划本身有缺陷（步骤错误、顺序错误、工具选错、入参错误）→ 惩罚计划，累计失败。
- `ENVIRONMENT`：环境问题（无网络、窗口未就绪、第三方服务异常）→ 不惩罚计划，仅记录。

## 6. 失败阈值与删除/禁用机制

- 计划、步骤、工具三者同质，都参与失败统计：**同一 `PLAN`（非环境）原因失败累计 3 次**（对齐现有 `qdrant.episode.failure-threshold=3` 及生成工具连续失败删除逻辑）→ **删除该 Unit**。
- **删除后自动降级到 `FALLBACK` 目标单元**（"这个步骤不行，换另一个"）；若需保留失败轨迹则同时建 `DISABLES` 边。
- `ENVIRONMENT` 类失败**不计入**阈值，只作为环境提示（`notes`）留存。
- **MCP 工具不参与此机制**：失败只记录，不删除、不禁用、无 FALLBACK（稳定基础设施）。
- 复用计划时，递归展开 `CONTAINS` 的同时查询 `DISABLES` / `FALLBACK`：**跳过被禁用的目标、改用替代目标**，规避失败成为图查询的一部分，不再依赖 AI 读文本判断。

## 7. AI 生成策略（保证数据质量）

- 层级太深、AI 单次生成树形结构质量差时，**允许多次少量生成、最后拼接**。
- 即：先让 AI 生成顶层步骤，再逐个让 AI 展开每个步骤的子步骤/工具，最后按 `order` 拼成完整树。
- 每次生成只覆盖一小段，降低单次 JSON 复杂度和出错率，保证数据质量优先于生成速度。
- **JSON 格式约束**：每次生成的 JSON 必须包含 `parentUnitId`（挂到哪个父步骤）和 `order`（在该父步骤下的顺序）；拼接时以 `parentUnitId + order` 为唯一锚点。
- **拼接校验**：系统验证 `parentUnitId + order` 无重复、无断层（`order` 连续，如 1、2、3、4 不断号），避免子步骤不知挂到哪个父步骤。

## 8. 执行与数据流传递

- `params`（入参签名）非必填：叶子工具可不带参，中间步骤/计划可带参（如 `{app:"微信"}`）。
- `outputSignature`（输出签名）：声明本 Unit 执行后**产出哪些变量**（如 `{weather:"String"}`）。
- **数据流引用**：后续步骤的 `params` 里可用 `$stepName.varName` 引用前序步骤的输出（如 `$查天气.weather`），形成真正的数据流，而非只做"用户输入 → 底层工具"的单向传递。
- **递归执行器数据流**：按 `CONTAINS` 顺序执行每个步骤 → 把其输出写入当前作用域 → 后续步骤的 `$stepX.var` 解析为实际值。
- **参数传递**：计划/步骤/工具任意层级之间，都可根据当前需求传参；父级把变量值传给子级（`$var` 替换）。
- **变量作用域**：子步骤可访问父步骤及**前序兄弟步骤已产出**的变量（变量提升 + 前序输出可见）。
- **防环**：递归展开时记录已访问的 `unitId` 集合，遇到重复引用立即报错并中止。
- **深度限制**：最大递归深度默认 5 层，超过即中止；AI 判断当前为超大型任务（5 层不够）时，可临时提升到 10 层。

## 9. 存储分工与双写事务

| 存储 | 职责 |
|---|---|
| **Neo4j** | 存结构：Unit 节点 + `CONTAINS`（有序）/ `DISABLES`（无序）/ `FALLBACK` 关系 + FailureCause 节点 |
| **Qdrant** | 存语义向量：embed `matchText`，做"用户输入→命中哪个 Unit"的检索入口 |

- Qdrant point id 与 Unit 的 `unitId` 一致，检索命中后按 `unitId` 回 Neo4j 递归展开。

**双写事务策略**：
- 写顺序：**先写 Neo4j，再写 Qdrant**。
- Qdrant 写失败 → **回滚 Neo4j**，或将该 Unit **标记为待同步**。
- **降级方案**：Qdrant payload 里缓存一层结构摘要（如直接子步骤的 `unitId` 列表），Neo4j 暂时不可用时可用该摘要降级展开。

## 10. 迁移策略

- **旧数据直接清空**：不再兼容旧扁平 Episode，下次探索从最小步骤开始重跑、逐步累积。
- 从小步骤（如"打开微信"）开始积累，被多个计划引用，越引用越稳定，逐步长成完整计划。
