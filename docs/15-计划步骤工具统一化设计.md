# 计划-步骤-工具统一化设计（图化记忆结构）

> **状态**：设计稿 v1.7，待交叉验证
> **目标**：用"统一对象 + 有序引用 + 无序禁用 + 随时注册 + 脚本化执行 + 异步生成 + 探索同构"的图结构，替换当前 Qdrant 扁平 Episode。

---

## 1. 背景与问题

当前经验闭环（Episode）存在三个结构性问题：

1. **扁平冗余**：完整 `toolCalls` 序列整体塞进 Qdrant payload。一个通用步骤被 N 个计划复用就要存 N 份，且无法单独复用"某一步"。
   2. **复用粒度单一**：只能复用整个 Episode，不能复用其中的子步骤；匹配靠硬编码关键词，命中率低。
   3. **失败经验与计划脱节**：失败教训存成独立文本，不挂在具体计划/步骤上，无法在复用计划时自动规避。

---

## 2. 核心设计理念

1. **递归 Plan（一切皆 Plan）**：Plan 递归嵌套 Plan，最原子的 Plan 就是 `@Tool`。计划 = 大 Plan，步骤 = 子 Plan，工具 = 原子 Plan——三者本质同一，只是递归层级不同。
   2. **随时注册 + 按需选择**：所有 Unit 可随时注册进入工具分类树，和现有工具一样参与分类门禁；规划时选哪个分类，就注册哪个分类下的 Unit，不一口气全量注入。
   3. **稳定层区分**：只有 MCP 工具是稳定基础设施，不可删；计划/步骤/动态工具是动态层，可删。
   4. **正向有序引用**：计划按 1→2→3→4 顺序包含步骤，步骤可递归包含子步骤或工具。
   5. **负向无序禁用**：失败经验固化为图上的"禁用边"，复用计划时自动跳过被禁用的步骤。
   6. **失败原因独立对象**：网络、环境、原因、入参、分析、归类全部结构化，归类为"计划原因"的失败累计达阈值即触发禁用/删除。
   7. **成功沉淀与差异更新**：执行成功后若含新工具，总结为统一格式的 Unit；与已有计划差异仅在某一步时，只记录差异点，不整体复制。
   8. **失败成功步骤提取**：执行失败时，提取已成功步骤总结为可复用 Unit；复用已有 FailureCause，记录建议替代方案。
   9. **异步生成不阻塞**：所有 Unit 的生成、沉淀、更新操作均在后台线程池执行，不阻塞用户交互。
   10. **脚本化执行**：简单、稳定、无数据流依赖的计划，生成时编译为线性脚本，执行时零递归、零 AI 参与。
   11. **探索模式同构**：自主探索也走 Unit 逻辑；单独选中一个 Plan 时，必须声明"优化"或"验证"，并记录次数。

## 3. 统一对象模型（Unit）

所有计划/步骤/工具都用一个统一对象表示，靠 `unitKind` 区分，格式完全一致。

| 字段 | 类型 | 说明 |
|---|---|---|
| `unitId` | String | 业务 UUID，对齐 Qdrant point id |
| `unitKind` | enum | `TOOL` / `PLAN_STEP` / `MCP_TOOL` |
| `matchText` | String | 匹配语言字段，embedding **只对此字段生成向量**，默认取 `goal`，区分度不足时 AI 重写加区别词 |
| `goal` | String | 说清要达到什么目的 |
| `description` | String | 补充描述 |
| `notes` | List\<String\> | 注意点、失败教训提示、变体说明 |
| `params` | Map\<String,String\> | 入参签名，**非必填**，被引用的步骤也可有自己的入参 |
| `outputSignature` | Map\<String,String\> | 输出签名，声明本 Unit 执行后产出哪些变量 |
| `toolName` | String | `unitKind` 为 `TOOL` / `MCP_TOOL` 时指向实际工具名 |
| `scriptable` | boolean | 是否可脚本化执行 |
| `script` | List\<ToolCallLog\> | 预编译线性脚本；`scriptable=true` 时执行此列表 |
| `successCount` | int | 成功次数 |
| `failureCount` | int | 失败次数（**仅计 PLAN 原因**） |
| `stability` | double | successCount / (successCount + failureCount) |
| `failureCauses` | List\<引用\> | 失败原因引用列表 |
| `explorationRecords` | List\<ExplorationRecord\> | 探索模式操作记录 |
| `status` | enum | `ACTIVE` / `ARCHIVED` |

### 3.1 ExplorationRecord（探索记录）

| 字段 | 类型 | 说明 |
|---|---|---|
| `recordId` | String | UUID |
| `declareType` | enum | `VALIDATE`（验证）/ `OPTIMIZE`（优化） |
| `validateCount` | int | 该 Unit 累计验证次数 |
| `optimizeCount` | int | 该 Unit 累计优化次数 |
| `lastValidateResult` | String | 最近一次验证结果 |
| `lastOptimizeResult` | String | 最近一次优化结果 |
| `timestamp` | long | 发生时间 |

- 探索模式单独选中一个 Unit 时，**必须显式声明 `declareType`**，不允许默认值。
  - 每次声明执行后追加一条记录，**仅作追溯用途**，不单独触发删除或禁用。
  - 删除/禁用仍只看 PLAN 失败次数（阈值 3）。

### 3.2 `unitKind` 在规划期 vs 执行期的角色

| 阶段 | `unitKind` 的用途 |
|---|---|
| **规划期** | AI 区分三类：`PLAN_STEP`（优先复用）、`TOOL`（按需补充）、`MCP_TOOL`（稳定底座） |
| **执行期** | `TOOL` / `MCP_TOOL` → 原子直接执行；`PLAN_STEP` → 递归展开或执行 `script` |

### 3.3 随时注册 + 分类门禁

- **随时注册**：Unit 生成后即进入工具注册表，和现有 `@Tool` 一样参与分类树构建。不批量预注册，不一口气全量注入。
  - **分类混排**：`PLAN_STEP` 和原子工具统一参与云端分类，展示时加标记：`[组合]` 表示 PLAN_STEP，`[工具]` 表示 TOOL/MCP_TOOL。
  - **按需注册（选哪个注册哪个）**：所有 Unit 都进工具分类；规划期分类浏览选中后，才把对应 Unit 的 `ToolCallback` 注入本轮 `toolCallbacks`，未选中的不注入，不一口气全量注册。
  - **包装工具**：每个 `PLAN_STEP` 包装为特殊工具，`call()` 指向万能执行器 `executePlanStep(unitId, paramsJson)`。工具描述包含 `goal`、内部步骤列表、适用场景。

**包装工具描述示例：**

```
工具名: plan_find_and_click_text

描述: [组合] 在屏幕上查找指定文字并点击。内部按顺序执行：
  1) ocrScreen - OCR识别屏幕文字
  2) findTextOnScreen - 定位目标文字坐标
  3) leftClick - 鼠标点击该坐标
适用场景：需要根据屏幕上的文字定位按钮并点击时，优先用这个组合步骤。

参数:
  targetText (String, 必填) - 要查找并点击的文字
```

**示例（发消息计划）：**

```
Unit[PLAN_STEP] "发消息"
  ├─ CONTAINS(1) → Unit[PLAN_STEP] "打开微信"   params:{app:"微信"}
  │                 ├─ CONTAINS(1) → Unit[TOOL] launchApp
  │                 └─ CONTAINS(2) → Unit[TOOL] findFriend
  └─ CONTAINS(2) → Unit[PLAN_STEP] "输入并发送" params:{text:"$message"}
                    └─ CONTAINS(1) → Unit[TOOL] typeText
```

## 4. 图结构

### 4.1 节点

| 节点 | 说明 |
|---|---|
| `Unit` | 统一节点，`unitKind` 区分类型 |
| `FailureCause` | 失败原因独立对象 |

### 4.2 关系

| 关系 | 方向 | 有序 | 属性 |
|---|---|---|---|
| `CONTAINS` | Unit → Unit | **有序** | `order`（int） |
| `DISABLES` | Unit → Unit | 无序 | `reason`、`failCount`、`condition` |
| `FALLBACK` | Unit → Unit | 无序 | `priority`（可选） |

- `CONTAINS`：按 order 顺序执行。
  - `DISABLES`：挂所有层，但不挂 MCP 工具。
  - `FALLBACK`：仅在被 DISABLES 时启用，且只使用一次，不递归，防循环。

---

## 5. 失败原因对象（FailureCause）

| 字段 | 类型 | 说明 |
|---|---|---|
| `causeId` | String | UUID |
| `network` | String | 网络快照 |
| `environment` | String | 环境快照 |
| `reason` | String | 失败原因描述 |
| `inputArgs` | String | 失败时入参快照 |
| `analysis` | String | AI 分析结论 |
| `category` | enum | `PLAN` / `ENVIRONMENT` |
| `timestamp` | long | 发生时间 |
| `suggestedUnitIds` | List\<String\> | 建议替代 Unit 引用，不建独立实体 |

**归类**：
- `PLAN`：步骤错、顺序错、工具错、参数错 → 惩罚，累计失败。
  - `ENVIRONMENT`：网络、窗口、第三方异常 → 不惩罚，只记录。

---

## 6. 失败处理

- **同一 PLAN 原因累计失败 3 次** → 删除该 Unit。
  - 删除后自动降级到 `FALLBACK` 目标；需保留轨迹则建 `DISABLES` 边。
  - `ENVIRONMENT` 失败不计入阈值，只写入 `notes`。
  - **MCP 工具**：失败只记录，不删除、不禁用、无 FALLBACK。
  - **成功步骤提取**：失败时提取已成功的前 N-1 步，总结为 PLAN_STEP 沉淀。
  - **FailureCause 复用**：先查库，有则引用并加计数，无则新建。
  - **suggestedUnitIds**：指向替代 Unit，不建独立实体。

---

## 7. AI 生成策略

### 7.1 多次少量生成 + 拼接

- 层数深时，先生成顶层步骤，再逐个展开子步骤，最后按 order 拼接。
  - 每次 JSON 必须含 `parentUnitId` 和 `order`，以 `parentUnitId + order` 为锚点。
  - 拼接校验：无重复、无断层。

### 7.2 脚本化判定

生成 PLAN_STEP 时判断是否满足**全部条件**：

1. 无递归子步骤（都是叶子 TOOL/MCP_TOOL）
   2. 无数据流依赖（不引用 `$stepX.var`）
   3. 步骤数 ≤ 5，或 `successCount ≥ 5 && stability > 0.9`
   4. 无 FALLBACK / DISABLES 关系

满足 → `scriptable=true`，生成线性 `script`，执行时直接遍历，零递归零 AI。

### 7.3 异步生成与线程池

- 独立线程池 `planGenerationPool`：核心 2，最大 4，有界队列 100，`CallerRunsPolicy`。
  - 主流程提交异步任务后立即返回，不阻塞用户。
  - **生成中的单元不落库**：全部成功后才双写，失败直接丢弃。

## 8. 执行与数据流

### 8.1 两种执行路径

| 路径 | 条件 | 方式 |
|------|------|------|
| 脚本化 | `scriptable=true` | 遍历 `script`，逐条调用 |
| 递归展开 | `scriptable=false` | 加载 CONTAINS 树，递归执行 |

统一入口 `executePlanStep(unitId, paramsJson)` 内部按 `scriptable` 分流。

### 8.2 脚本化执行

- 遍历 `script`，变量从 `paramsJson` 替换。
  - 某步失败 → 记录，停止后续。
  - 成功后更新计数。

### 8.3 递归展开执行

- `params` 非必填；`outputSignature` 声明产出变量。
  - 数据流：后续步骤用 `$stepName.varName` 引用前序输出。
  - 变量作用域：子步骤可访问父步骤及前序兄弟步骤的输出。
  - 防环：记录 visited unitId，重复即中止。
  - 深度限制：最大 5 层，可配置。

## 9. 探索模式同构

探索模式**不另起一套执行管线**，复用 §8 同一套 Unit 执行逻辑。区别仅在任务来源和声明类型：

| 维度 | 普通任务 | 探索任务 |
|------|---------|---------|
| 任务来源 | 用户指令 / 对话 | 自主探索调度器 |
| 选中 Unit 后是否声明 | 不需要 | **必须声明 `VALIDATE` 或 `OPTIMIZE`** |
| 执行路径 | 脚本化 / 递归 | 脚本化 / 递归（同一套） |
| 结果处理 | 沉淀 / 失败处理 | 沉淀 / 失败处理 + 探索记录 |

### 9.1 声明类型

| 声明类型 | 含义 | 行为 |
|---------|------|------|
| `VALIDATE` | 确认该 Unit 当前是否仍有效 | 正常执行，不主动修改 Unit；记录结果 |
| `OPTIMIZE` | 尝试改进该 Unit | 执行并对比效果；若发现更优步骤，沉淀差异更新 |

### 9.2 记录规则（沿用之前设计值）

- 每次声明执行后追加一条 `ExplorationRecord`。
  - `validateCount` / `optimizeCount` 各自累计。
  - 记录仅作追溯，不单独触发删除/禁用。
  - 删除/禁用仍只看 PLAN 失败次数（阈值 3）。
  - 脚本化阈值沿用：`successCount ≥ 5 && stability > 0.9`。
  - 递归深度上限沿用：5 层。
  - 脚本化步骤数上限沿用：≤ 5 步。

## 10. 存储分工与一致性

| 存储 | 职责 |
|---|---|
| **Neo4j** | Unit 节点 + CONTAINS / DISABLES / FALLBACK + FailureCause |
| **Qdrant** | embed `matchText`，用户输入→命中 Unit 的检索入口 |

- Qdrant point id 与 `unitId` 一致，命中后回 Neo4j 展开。

**一致性策略（最终一致性）**：
- 写顺序：**先写 Neo4j，再写 Qdrant**。
  - Qdrant 写失败 → **重试 N 次**，仍失败则记录日志，不强制回滚 Neo4j。
  - Qdrant 缺数据只影响"语义检索入口"，不影响结构完整性。
  - 提供后台补偿任务：定期扫描 Neo4j 中"未被 Qdrant 索引"的 Unit，补写 Qdrant。

## 12. 成功沉淀与差异更新

执行成功后，若含新工具或轨迹与已有计划不同，触发沉淀：

1. 收集实际调用序列（工具名、入参、输出、顺序）。
   2. 总结为 PLAN_STEP Unit，格式统一。
   3. 按 §7.2 判断是否脚本化。
   4. 差异检测与合并：
      - 完全相同 → 仅更新 `successCount`、`stability`。
      - 整体相同、某步不同 → 在 `notes` 写清差异，必要时建 `FALLBACK`。
      - 差异较大 → 新建 Unit。
   5. 新工具先注册为 TOOL Unit，再通过 CONTAINS 挂接。
