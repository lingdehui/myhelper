# 05 - 记忆与向量系统

## 1. 系统架构

### 1.1 双引擎架构

记忆与人格层采用 **Qdrant（向量数据库）+ Neo4j（图数据库）** 双引擎架构，分别承担不同的记忆职责：

| 维度 | Qdrant（向量） | Neo4j（图） |
|------|---------------|-------------|
| 核心能力 | 语义搜索、相似记忆检索 | 实体关系、知识图谱 |
| 存储内容 | 对话历史、Episode 执行轨迹、嵌入向量 | 设备实体、用户偏好、控制关系 |
| 检索方式 | 余弦相似度向量检索 + Payload Filter | Cypher 查询、图遍历 |
| 典型场景 | "上次我说过什么"、"类似的任务怎么执行的" | "客厅有哪些设备"、"用户喜欢的温度" |

### 1.2 数据流向图

```
用户输入
    │
    ├──▶ EmbeddingService ──▶ Qdrant 向量检索
    │                           │
    │                           ├── 命中 Episode ──▶ PlanMatcher ──▶ PlanExecutor
    │                           │                                                      │
    │                           │                                                      ├── 成功 ──▶ ReflectService.reflectSuccess()
    │                           │                                                      │              │
    │                           │                                                      │              └──▶ EpisodeCacheService.activateDraft() ──▶ UnitLearner.learnAsync()（提取 ATOMIC）
    │                           │                                                      │
    │                           │                                                      └── 失败 ──▶ ReflectService.reflectFailure()
    │                           │                                                                     │
    │                           │                                                                     ├── 计划问题 ──▶ recordFailure(isPlanIssue=true)
    │                           │                                                                     └── 环境问题 ──▶ recordFailure(isPlanIssue=false)
    │                           │
    │                           └── 未命中 ──▶ AI 新规划 ──▶ createDraft() ──▶ 执行 ──▶ activateDraft() / failDraft()
    │
    └──▶ MemoryService
            │
            ├──▶ KnowledgeGraphService ──▶ Neo4j
            │       ├── DeviceNode（设备实体 CRUD）
            │       └── UserPreferenceNode（偏好学习/查询）
            │
            └──▶ VectorMemoryService ──▶ Qdrant
                    ├── remember() 存储对话记忆
                    └── recall() 语义搜索历史
```

## 2. 向量系统

### 2.1 EmbeddingService（嵌入服务）

**文件位置**：`src/main/java/com/example/myhelper/memory/vector/EmbeddingService.java`

**职责**：调用 Ollama 嵌入 API 将文本转换为语义向量，供 Qdrant 检索使用。

| 属性 | 说明 |
|------|------|
| 外部依赖 | Ollama（`http://localhost:11434`） |
| 默认模型 | `nomic-embed-text`（768 维） |
| 配置项 | `embedding.model`（可通过配置文件覆盖） |

**核心方法**：

- `embed(String text)` — 单文本嵌入，内部委托给 `embedBatch`
- `embedBatch(List<String> texts)` — 批量嵌入，逐个调用 Ollama `/api/embeddings` 接口
  - 将 Ollama 返回的 `Double` 转换为 `Float`
  - 异常或空响应时返回零向量（768 维全 0），不中断主流程

**零向量降级**：当 Ollama 不可用时返回 768 维全零向量，确保系统降级运行，日志中输出 `⚠️` 警告。

### 2.2 VectorMemoryService（向量记忆服务）

**文件位置**：`src/main/java/com/example/myhelper/memory/vector/VectorMemoryService.java`

**职责**：面向 Qdrant 集合的通用 CRUD 服务，用于对话历史的向量存储与检索。

**构造依赖**：
- `WebClient`（Qdrant REST 客户端）
- `qdrantCollectionName` Bean（集合名）

**核心数据结构**：

```java
public record SearchResult(String text, float score, Map<String, Object> metadata)
```

**核心方法**：

| 方法 | 说明 |
|------|------|
| `store(String text, List<Float> vector, Map<String, String> metadata)` | 存储一条记忆：文本 + 向量 + 元数据，使用 `AtomicLong` 生成自增 ID |
| `search(List<Float> queryVector, int limit)` | 语义搜索，返回 Top-N 最相关的 `SearchResult` |
| `count()` | 获取集合中的记忆总数 |

**Payload 结构**：
```
{
  "text": "原始文本",
  "type": "user_input | ai_response | tool_call",
  "timestamp": "1700000000000"
}
```

**API 路径**：
- 写入：`PUT /collections/{name}/points?wait=true`
- 搜索：`POST /collections/{name}/points/search`
- 统计：`GET /collections/{name}`

### 2.3 QdrantConfig（Qdrant 配置）

**文件位置**：`src/main/java/com/example/myhelper/memory/vector/QdrantConfig.java`

**职责**：Spring 配置类，初始化 Qdrant 连接与集合。

**配置项**：

| 配置键 | 默认值 | 说明 |
|--------|--------|------|
| `qdrant.host` | `localhost` | Qdrant 服务器地址 |
| `qdrant.port` | `6333` | Qdrant REST API 端口 |
| `qdrant.collection` | `desktop-memory` | 集合名称 |
| `qdrant.vector-size` | `768` | 向量维度（与嵌入模型一致） |

**Bean 定义**：

| Bean | 说明 |
|------|------|
| `qdrantWebClient` | 基于 `WebClient` 的 Qdrant REST 客户端 |
| `qdrantCollectionName` | 集合名称字符串 |
| `qdrantVectorSize` | 向量维度整数 |
| `qdrantInitCollection` | 启动时自动检查并创建集合（如不存在），距离度量使用 **Cosine** |

**集合初始化逻辑**：
1. `GET /collections/{name}` 检查集合是否存在
2. 不存在则 `PUT /collections/{name}` 创建，指定向量维度和 Cosine 距离
3. 已存在则跳过

### 2.4 集合设计

系统使用多个 Qdrant 集合，各司其职：

| 集合 | 说明 | 向量维度 | 距离度量 |
|------|------|----------|----------|
| `desktop-memory`（由 `QdrantConfig` 创建） | 通用对话记忆 | 768 | Cosine |
| `episodes`（由 `EpisodeCacheService` 创建） | Episode 执行轨迹缓存 | 768 | Cosine |
| `failure-patterns`（由 `EpisodeCacheService` 创建） | 失败模式聚合结果 | 768 | Cosine |
| `tool-categories`（由 `ToolCategoryService` 创建） | 工具动态分类向量存储 | 768 | Cosine |

> **注意**：当前代码中 `EpisodeCacheService` 使用独立的 `episodes` 集合，而 `VectorMemoryService` 使用 `desktop-memory` 集合。两者共享同一 Qdrant 实例和向量维度。

## 3. 可执行单元（Episode）

Episode 系统借鉴 **ExpeL（经验学习）** 和 **MUSE（自演化 Agent）** 的思想，将每次成功执行的完整任务轨迹持久化到 Qdrant，下次相似请求通过向量检索直接复用。

### 3.1 Episode 数据结构

**文件位置**：`src/main/java/com/example/myhelper/memory/vector/episode/Episode.java`

**设计理念**：用户核心设计思想——"步骤=小计划→统一抽象→分形结构"。

**字段说明**：

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | `String` | UUID，同时作为 Qdrant point ID |
| `userInput` | `String` | 用户原话（用于重新 embed 和展示） |
| `selectedToolNames` | `List<String>` | 选中的工具名列表 |
| `missingDescriptions` | `List<String>` | 缺失的工具描述 |
| `toolCalls` | `List<ToolCallLog>` | 实际工具调用轨迹（COMPOSITE 的执行脚本） |
| `aiResponse` | `String` | AI 最终回复（截断到 500 字符） |
| `successLesson` | `String` | 成功经验（AI 反思总结，30 字内，下次复用时作为 hint） |
| `failureLesson` | `String` | 失败教训（AI 反思总结，30 字内，下次复用时作为警示） |
| `signature` | `Map<String, String>` | 变量签名：变量名 → 来源（"user_input" 表示从用户输入提取） |
| `unitType` | `UnitType` | COMPOSITE（完整计划）或 ATOMIC（通用步骤） |
| `isGeneric` | `boolean` | 是否是通用步骤（被≥3个 composite 引用时自动标记） |
| `parentIds` | `List<String>` | 被哪些大 Episode 引用（用于通用步骤提取和反向查找） |
| `successCount` | `int` | 累计成功次数 |
| `failureCount` | `int` | 累计失败次数 |
| `archived` | `boolean` | 是否已归档 |
| `timestamp` | `long` | 创建时间戳（毫秒） |
| `stability` | `double` | 冗余字段：`successCount/(success+failure)`，用于 Qdrant Filter |
| `status` | `EpisodeStatus` | DRAFT / ACTIVE / FAILED |
| `canScript` | `boolean` | 是否可脚本化（`successCount ≥ 5` 且 `stability > 0.9` 时为 true） |
| `failedStepIndex` | `int` | 失败步位置（-1 = 未失败/成功；≥0 = 第 N 步失败） |

**UnitType（单元类型）**：

| 类型 | 说明 |
|------|------|
| `COMPOSITE` | 复合计划，包含有序的步骤（toolCalls 脚本），可变量化复用（如"微信发消息"，变量 `contact`/`message`） |
| `ATOMIC` | 原子步骤，从 COMPOSITE 中提取的通用小计划（如"输入文字"，被≥3个 COMPOSITE 引用时自动标记 `isGeneric=true`） |

**EpisodeStatus（生命周期状态）**：

| 状态 | 说明 |
|------|------|
| `DRAFT` | 草稿：执行中创建，尚未确认结果 |
| `ACTIVE` | 活跃：执行成功，可被检索复用 |
| `FAILED` | 失败：执行失败但保留已执行步骤，供后续分析 |

**关键计算方法**：

- `computedStability()` — Java 端实时计算 `successCount / (successCount + failureCount)`，不依赖存储的 `stability` 字段（因为 Qdrant Payload Filter 不支持表达式计算，所以 `stability` 作为冗余字段存储）
- `isComposite()` — 判断是否为 COMPOSITE 类型
- `isScriptable()` — 判断是否可脚本化执行：`canScript && status == ACTIVE && toolCalls 非空`

**ToolCallLog（工具调用日志）**：

**文件位置**：`src/main/java/com/example/myhelper/memory/vector/episode/ToolCallLog.java`

作为 Episode 轨迹的最小单元：

```java
public record ToolCallLog(
    String toolName,   // 工具名
    String args,       // 工具入参 JSON（截断到 500 字符）
    String result,     // 工具返回值（截断到 500 字符）
    boolean success,   // 是否调用成功
    long durationMs    // 调用耗时（毫秒）
)
```

### 3.2 EpisodeCacheService（缓存服务）

**文件位置**：`src/main/java/com/example/myhelper/memory/vector/episode/EpisodeCacheService.java`

**职责**：Episode 的持久化、向量检索、失败统计与自动归档。核心服务，实现 `Plan → Execute → Reflect → Memorize` 完整闭环。

**配置项**：

| 配置键 | 默认值 | 说明 |
|--------|--------|------|
| `qdrant.episodes-collection` | `episodes` | Episode 集合名称 |
| `qdrant.vector-size` | `768` | 向量维度 |
| `qdrant.episode.similarity-threshold` | `0.65` | 相似度阈值 |
| `qdrant.episode.stability-threshold` | `0.6` | 稳定度过滤阈值 |
| `qdrant.episode.failure-threshold` | `3` | 失败次数归档阈值 |
| `qdrant.episode.top-k` | `3` | 检索返回数量 |
| `qdrant.episode.script-success-threshold` | `5` | 脚本化所需成功次数阈值 |

#### 核心流程

**1. 向量检索相似 Episode（`findSimilarEpisode`）**

```
用户输入 → EmbeddingService.embed() → Qdrant 搜索
                                         │
                                         ├── Filter: archived=false
                                         │           stability ≥ 0.6
                                         │           status = ACTIVE
                                         │
                                         ├── score_threshold ≥ 0.65
                                         └── 结果按 computedStability() 排序，返回最佳
```

**2. DRAFT → ACTIVE 生命周期**

```
createDraft() → 同步写入 Qdrant（status=DRAFT）
        │
        ▼
    执行任务
        │
        ▼
activateDraft() → 异步更新：
    ├── toolCalls（完整轨迹）
    ├── aiResponse（截断到 500）
    ├── successLesson（经验总结）
    ├── successCount+1 → stability 重算
    ├── status → ACTIVE
    └── 如果 successCount ≥ 5 且 stability > 0.9 → canScript=true
```

**3. DRAFT → FAILED 生命周期**

```
failDraft() → 异步更新：
    ├── toolCalls（已执行的部分轨迹）
    ├── failureLesson（教训总结）
    ├── failedStepIndex（失败步位置）
    └── status → FAILED
```

**4. 失败归因处理（`recordFailure`）**

```
ReflectService.reflectFailure() 归因
        │
        ├── isPlanIssue = true（计划问题）
        │     ├── failureCount+1
        │     ├── stability 重算
        │     ├── stability ≤ 0.9 → canScript 降级为 false
        │     └── failureCount ≥ 3 或 stability < 0.3 → archived=true
        │
        └── isPlanIssue = false（环境问题）
              └── 仅存储 failureLesson，不惩罚计划
```

**5. 成功计数（`incrementSuccess`）**

对已存在的 ACTIVE Episode 进行成功计数 +1，不重置 failureCount，让 stability 自然衰退。当达到脚本化阈值时自动升级。

**所有写操作均通过 `CompletableFuture.runAsync()` 异步执行**，Qdrant 故障吞异常不传染主流程。

### 3.3 PlanMatcher（计划匹配器）

**文件位置**：`src/main/java/com/example/myhelper/memory/vector/episode/PlanMatcher.java`

**职责**：AI 判断 Episode 是否适用于当前输入，并提取变量值。不直接复用命中的 Episode，而是先经 AI 二次确认。

**构造**：使用 `ChatClient`，系统提示为 "你是计划匹配判断器，判断已有计划是否适用于当前用户请求，并提取变量。"

**核心方法 `match(String userInput, Episode episode)`**：

1. 校验 Episode 有可执行步骤（`toolCalls` 非空）
2. 构造 Prompt，包含：
   - 用户请求
   - 计划用途（Episode 的 `userInput`）
   - 计划步骤列表（编号 + 工具名 + 参数）
   - 需要的变量列表（`signature` 的 key 集合）
3. 要求 AI 返回严格 JSON：
   ```json
   {"applicable": true/false, "variables": {"变量名": "变量值"}, "reason": "简要理由"}
   ```
4. 解析 JSON（容错：去除 markdown 代码块标记）

**MatchResult 结构**：

```java
public record MatchResult(boolean applicable, Map<String, String> variables, String reason)
```

- `notApplicable(reason)` — 快捷构造不适用结果
- `applicable(variables, reason)` — 快捷构造适用结果

**降级策略**：AI 调用失败或 JSON 解析失败时返回 `notApplicable`，降级到 AI 新规划路径。

### 3.4 PlanExecutor（计划执行器）

**文件位置**：`src/main/java/com/example/myhelper/memory/vector/episode/PlanExecutor.java`

**职责**：当 Episode 的 `canScript=true`（稳定度高）时，跳过 AI 决策，直接按 toolCalls 脚本逐步调用工具。

**核心方法**：

| 方法 | 说明 |
|------|------|
| `executeScript(Episode, variables, allTools)` | 按计划脚本逐步执行（从第 0 步开始） |
| `executeFromStep(Episode, fromStep, variables, allTools)` | 从失败步之后继续执行（分段继续） |

**变量替换机制**：

toolCalls 的 args 中的 `$varName` 占位符会被替换为 PlanMatcher 提取的变量值：
```
{"name":"$contact"} → {"name":"张三"}
```

**执行流程**：

```
for each step in episode.toolCalls:
    1. 变量替换 resolveVariables(step.args, variables)
    2. 查找工具 findTool(step.toolName, allTools)
    3. 调用 tool.call(resolvedArgs)
    4. 记录 ToolCallLog（成功/失败 + 耗时）
    5. 某步失败 → 立即返回 ExecutionResult.failed
```

**ExecutionResult 结构**：

```java
public record ExecutionResult(
    boolean success,           // 是否全部成功
    List<ToolCallLog> executedSteps,  // 已执行的步骤日志
    int failedStepIndex,       // 失败步位置（-1=全部成功）
    String errorMessage        // 失败错误信息
)
```

**失败处理**：
- 工具不存在 → 返回失败（`failedStepIndex` 为当前步）
- 工具抛异常 → 捕获并返回失败，`executed` 中保留已成功执行的步骤
- 上层可据此实现"分段继续"

### 3.5 ReflectService（反思服务）

**文件位置**：`src/main/java/com/example/myhelper/memory/vector/episode/ReflectService.java`

**职责**：ExpeL/MUSE 闭环中的 Reflect 环节。每次执行后让 AI 反思提取经验教训。

**构造**：使用 `ChatClient`，系统提示为 "你是经验反思总结器，用简洁的一句话总结任务执行的经验教训。"

#### 成功反思（`reflectSuccess`）

```
输入: userInput + toolCalls（执行轨迹） + aiResponse
  │
  ▼
Prompt: 总结关键成功经验（30 字内）
  │
  ▼
返回: successLesson（供下次复用作为 hint）
```

#### 失败反思与归因（`reflectFailure`）

```
输入: userInput + toolCalls（可能部分执行） + errorMessage
  │
  ▼
Prompt: 分析失败原因，判断是计划问题还是环境问题
  │
  ▼
返回: FailureAnalysis(lesson, isPlanIssue)
  │
  ├── isPlanIssue=true  → 计划问题（步骤顺序错、工具选择错等）
  └── isPlanIssue=false → 环境问题（目标不存在、网络中断、权限不够等）
```

**FailureAnalysis 结构**：

```java
public record FailureAnalysis(String lesson, boolean isPlanIssue)
```

**归因规则**（AI 判定）：
- **计划问题**：步骤顺序错误、缺少必要中间步骤、工具选择错误、参数逻辑错误
- **环境问题**：目标不存在、网络中断、权限不够、应用未启动、元素未加载

**降级策略**：AI 调用失败时默认当作环境问题（`isPlanIssue=false`），不惩罚计划。

### 3.6 UnitLearner（通用步骤提取器） ✅

**文件位置**：`src/main/java/com/example/myhelper/memory/vector/episode/UnitLearner.java`

**职责**："越用越聪明"的关键——自动从多个 COMPOSITE episode 中发现可复用的公共子步骤，提取为 ATOMIC 通用单元。

**提取算法**：
1. 扫描所有 ACTIVE COMPOSITE episode（Qdrant scroll API，filter: status=ACTIVE, unitType=COMPOSITE, archived=false）
2. 构建工具名子序列频率统计：`key="toolA|toolB|..." → Set<episodeId>`
3. 过滤：子序列长度 ≥ 2 且出现次数 ≥ 3
4. 去重：检查是否已有相同的 ATOMIC 序列存在
5. 创建 ATOMIC episode（UnitType.ATOMIC, isGeneric=true, parentIds=源 episode ID 列表）

**触发时机**：每次 DRAFT→ACTIVE 成功后异步触发（`EpisodeCacheService.activateDraft` → `unitLearner.learnAsync()`），渐进式积累。

**ATOMIC 特征**：
- `unitType=ATOMIC`，`isGeneric=true`
- `parentIds` 记录被哪些 COMPOSITE 引用
- `stability=0.5`（初始中等，尚未单独验证）
- 可在 PlanMatcher 中被直接匹配为可执行步骤
- 存储在同一个 episodes collection 中（分形统一抽象）

**配置项**：

| 配置键 | 默认值 | 说明 |
|--------|--------|------|
| `qdrant.episode.generic-threshold` | `3` | 至少被 N 个 COMPOSITE 引用才提取为通用 ATOMIC |

### 3.7 FailureExperienceHandler（失败经验处理器）

**文件位置**：`src/main/java/com/example/myhelper/memory/vector/episode/FailureExperienceHandler.java`

**职责**：对失败经验进行滑动窗口聚合，当相似失败在短时间内重复出现时自动生成 FailurePattern。

**核心机制**：

```
每次失败 → handle(userInput, lesson, isPlanIssue, hasSalvaged, toolNames)
  │
  ├── 归一化 key = AiResponseUtils.normalizeKey(userInput)
  │
  ├── 滑动窗口: ConcurrentHashMap<String, LinkedBlockingDeque<Long>>
  │     key → 记录每次故障时间戳
  │     清理超出 1 小时的旧记录
  │
  ├── 去重检查: patternCache（Set<String>）避免重复生成
  │
  └── 计数 ≥ PATTERN_THRESHOLD(3) → 生成 FailurePattern
        └── EpisodeCacheService.saveFailurePattern()
              ├── Qdrant: upsertPointToCollection("failure-patterns", ...)
              └── Neo4j: failurePatternRepo.save(FailurePatternNode)
```

**FailurePattern 结构**：

```java
public record FailurePattern(
    String type,        // 失败类型（如 "目标网页URL不存在"）
    String description, // 模式描述
    String mitigation,  // 缓解建议
    int count,          // 触发次数
    long detectedAt     // 检测时间
)
```

**配置参数**：
- `WINDOW_SIZE_MS = 60 * 60 * 1000`（1 小时窗口）
- `PATTERN_THRESHOLD = 3`（3 次触发生成模式）

### 3.8 RuleInductionService（规则归纳服务）

**文件位置**：`src/main/java/com/example/myhelper/service/RuleInductionService.java`

**职责**：定时扫描 FailurePattern 和成功 Episode，调用 LLM 做跨案例归纳，生成通用规则。

**触发时机**：`@Scheduled(cron = "0 0 3 * * ?")` — 每天凌晨 3 点

**归纳流程**：

```
RuleInductionService.induceRules()
  │
  ├── 1. 扫描 FailurePattern
  │     EpisodeCacheService.searchFailurePatterns("归纳规则", 10)
  │     提取高频失败模式
  │
  ├── 2. 扫描成功 Episode
  │     EpisodeCacheService.getRecentSuccessfulEpisodeSummaries()
  │     提取近期成功案例摘要
  │
  ├── 3. LLM 跨案例归纳
  │     构建 Prompt: list<FailurePattern> + list<成功摘要> → 通用规则
  │     要求 AI 输出 JSON: [{summary, confidence, relatedTools}]
  │
  ├── 4. 去重检查
  │     RuleRepository.findBySummary() 是否存在
  │
  └── 5. 存入 Neo4j
        ruleRepository.save(new RuleNode(summary, confidence, source, relatedTools))
```

**RuleNode Neo4j 实体**：

| 字段 | 类型 | 说明 |
|------|------|------|
| `summary` | String | 规则摘要（唯一索引） |
| `confidence` | double | 置信度 0-1 |
| `source` | String | 来源：`from_failure_pattern` 或 `from_success_episode` |
| `relatedTools` | List\<String\> | 相关工具名 |
| `enabled` | boolean | 是否启用 |
| `created` | LocalDateTime | 创建时间 |

**规则注入**：`ToolPlanner.doPlan()` 从 RuleRepository 查询活跃规则，注入到 AI 规划 prompt 中。

### 4.5 KnowledgeGraphService（图谱服务）

**文件位置**：`src/main/java/com/example/myhelper/memory/graph/KnowledgeGraphService.java`

**职责**：封装 `DeviceRepository` 和 `UserPreferenceRepository` 的业务逻辑，提供设备管理与用户偏好学习的高层 API。

#### 设备管理

| 方法 | 说明 |
|------|------|
| `upsertDevice(name, type, room)` | 注册或更新设备。已存在则更新 room 和 lastSeen，不存在则新建 |
| `updateDeviceState(name, stateJson)` | 更新设备状态（JSON） |
| `addControlRelation(controllerName, targetName)` | 建立控制关系（A 控制 B） |
| `getRoomDevices(room)` | 查询房间内所有设备 |
| `getDevicesByType(type)` | 按类型查询设备 |
| `getAllDevices()` | 获取所有设备 |

#### 用户偏好

| 方法 | 说明 |
|------|------|
| `savePreference(category, key, value)` | 直接保存偏好（新建） |
| `learnPreference(category, key, value)` | **学习偏好**：已存在相同偏好则 `confidence + 0.1`（上限 1.0），否则新建（默认 confidence=0.6） |
| `getActivePreferences(category)` | 获取高置信度偏好（confidence ≥ 0.5） |
| `getScenePreferences(condition)` | 按触发条件查询场景偏好 |
| `getAllPreferences()` | 获取所有偏好 |

#### Repository 查询

**DeviceRepository** 自定义查询：

```
findDevicesInRoom(roomName)
    → MATCH (d:Device)-[:LOCATED_IN]->(room:Device) WHERE room.name = $roomName

findOnlineDevicesByType(type)
    → MATCH (d:Device {type: $type}) WHERE d.state IS NOT NULL

findControlledDevice(controllerName, targetName)
    → MATCH (a:Device)-[r:CONTROLS]->(b:Device)
      WHERE a.name = $controllerName AND b.name = $targetName
```

**UserPreferenceRepository** 自定义查询：

```
findActivePreferences(category, minConfidence)
    → MATCH (p:UserPreference {category: $category})
      WHERE p.trigger IS NOT NULL AND p.confidence >= $minConfidence

findByTriggerCondition(condition)
    → MATCH (p:UserPreference) WHERE p.trigger CONTAINS $condition
```

## 5. MemoryService（统一门面）

**文件位置**：`src/main/java/com/example/myhelper/memory/MemoryService.java`

**职责**：整合 `KnowledgeGraphService` + `VectorMemoryService` + `EmbeddingService`，提供统一的记忆层 API，对应架构中的"记忆与人格层"。

**依赖注入**：

```java
private final KnowledgeGraphService knowledgeGraph;
private final VectorMemoryService vectorMemory;
private final EmbeddingService embeddingService;
```

#### 知识图谱操作

| 方法 | 说明 |
|------|------|
| `registerDevice(name, type, room)` | 注册设备到 Neo4j |
| `learnPreference(category, key, value)` | 学习用户偏好（自适应置信度） |
| `getRoomDevices(room)` | 获取房间设备列表（返回格式化字符串：`"设备名 (类型)"`） |

#### 向量记忆操作

| 方法 | 说明 |
|------|------|
| `remember(content, type)` | 保存对话记忆到 Qdrant。`type` 取值：`user_input` / `ai_response` / `tool_call`。自动生成嵌入向量，附带 `type` 和 `timestamp` 元数据 |
| `recall(query, limit)` | 语义搜索相关记忆，返回 `List<SearchResult>` |
| `getContextSummary(currentQuery)` | 获取上下文摘要：自动对当前查询进行语义搜索（Top-3），返回格式化的历史记忆文本 |

**生成嵌入**：所有向量操作内部通过 `embeddingService.embed(text)` 生成 768 维向量（Ollama `nomic-embed-text` 模型）。

**典型使用场景**：

```java
// 注册新设备
memoryService.registerDevice("客厅灯", "light", "客厅");

// 学习用户偏好
memoryService.learnPreference("temperature", "空调默认温度", "26");

// 保存对话
memoryService.remember("把客厅灯打开", "user_input");
memoryService.remember("好的，已为您打开客厅灯", "ai_response");

// 获取上下文（注入到 AI Prompt 中）
String context = memoryService.getContextSummary("把灯关了");
```

## 附录：Qdrant vs Neo4j 职责边界

| 维度 | Qdrant（向量） | Neo4j（图） |
|------|---------------|-------------|
| 数据模型 | Point（id + vector + payload） | Node + Relationship |
| 存储内容 | 文本语义向量、Episode 轨迹 | 设备实体、偏好、控制关系 |
| 查询能力 | 余弦相似度 + Payload Filter | 图遍历、Cypher 模式匹配 |
| 优势 | "找相似"——语义模糊匹配 | "找关系"——结构化精确查询 |
| 典型 API | `POST /collections/{name}/points/search` | `MATCH (d:Device) WHERE ... RETURN d` |
| 写入方式 | `PUT /collections/{name}/points` | Spring Data Neo4j `save()` |

两者通过 `MemoryService` 门面统一对外暴露，上层仅与 `MemoryService` 交互，无需感知底层双引擎差异。

### 6.2 MemoryMaintenanceService（记忆维护）

**文件位置**：`src/main/java/com/example/myhelper/exploration/MemoryMaintenanceService.java`

**职责**：定期清理 Qdrant 中的低价值 Episode。

**触发**：`@Scheduled(cron = "${myhelper.memory-maintenance.cron:0 0 4 * * ?}")` — 默认凌晨 4 点。

**清理策略**：
- 计算 Qdrant 总占用率（episodes + failure-patterns 点数 / 10万上限）
- 占用率 ≥ threshold（0.7）→ 触发清理
- 目标：降至 target（0.5）
- 清理对象：`archived=true` 且 `stability < 0.1` 的 Episode
- 删除方式：`POST /collections/episodes/points/delete?wait=true`

### 6.3 配置项

**文件**：`src/main/resources/config/myhelper-exploration.yml`

```yaml
myhelper:
  memory-maintenance:
    enabled: true
    cron: 0 0 4 * * ?       # 可配置 cron
    threshold: 0.7
    target: 0.5
    weights:                 # 价值评分权重（预留）
      recency: 0.3
      usage: 0.3
      user-produced: 0.25
      dependency: 0.15
    retention-rules:         # 按来源保留天数（预留）
      user-task: 365
      autonomous-exploration: 90
      failure-pattern: 180
```
