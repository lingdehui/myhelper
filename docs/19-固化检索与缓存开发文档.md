# 固化检索与缓存模块

> 共同开发规则（2026-11-11 用户确认）：固定 LLM 文本集中到 LlmTexts；不用 Lambda，以可读性选择循环、方法和 switch，允许 `case ... ->`。所有任务继续前阅读[24-LLM文本与代码可读性规范](24-LLM文本与代码可读性规范.md)。

更新：2026-11-10。已实现独立 capability 包、根入口/每次规划后的检索、固定版本内容缓存及 Qdrant HTTP 仓储。生产合同匹配策略、真实嵌入及数据库装配仍需调用方提供；技能生成与发布不在本模块。

## 1. 已确认并实现的检索时机

```text
一次根任务入口
  → searchAtEntry：按用户目标查数据库一次
  → 整条匹配并可执行：直接运行
  → 否则交给模型

每次模型提交 PLAN
  → searchAfterPlanning
      → 用模型计划 goal 查询整条固化
      → 用每个 Step.goal 分别查询子节点固化
  → 匹配合同、加载固定版本，保存 PlanMatches
  → 执行时用当前绑定，已有能力跳过额外模型规划

下一轮模型再次提交 PLAN
  → 再次执行上述规划后检索
```

递归子任务进入模型循环，不重复根入口检索；COMPLETE、NEEDS_INPUT、等待前驱、工具回包不触发候选检索。固化定义展开也不是新模型规划，不重新做语义搜索。每次能力调用开始前另做 isAvailable 权威资格读取。

## 2. 实际接口与职责

| 代码 | 已实现职责 |
| --- | --- |
| CapabilityLookup | searchAtEntry(Query)、searchAfterPlanning(runId,revision,plan,input)、isAvailable(Ref)、cachedCount() |
| Repository | search(Query)、load(Ref)、isAvailable(Ref) |
| Matcher | matches(Query,Candidate)，必须由业务装配，不默认按分数放行 |
| QdrantCapabilityRepository | HTTP 向量查询、解析已有 payload.entity、权威读取固定 revision 和发布状态 |
| PlanMatches | 本次计划整条及 stepId 到 Match 的映射，由计划执行链持有 |
| 内容缓存 | Lookup 内部有限 LRU + TTL，按 namespace/id/revision 保存不可变 Definition |

Query 包含 runId、planRevision、stepId、goal、arguments、可选原始 Step。入口 stepId 为 $entry，整条为 $plan。子节点查询携带模型给出的工具名、类别、参数和绑定来源；未知上游结果不伪造为已知参数。实际检索文本来自 goal。

Candidate 包含固定 Ref、description、contract；Match 保留本次候选和可选的已选 Definition；Definition 为固定 Ref + TaskPlan。匹配器负责确认目标、输入/输出形状、作用范围和副作用等价。名称相同或语义相近不足以替换；无法确认时返回 false。执行阶段仍以实际绑定参数经过 Checks.allow 和结果验收。

当前组合输出为 stepId → {status,value,error}，没有额外输出映射字段；匹配器必须确保调用方能消费该形状。通用能力参数适配、分支条件、历史版本加载、依赖批量展开仍未实现。

可读性整理：$entry/$plan 提取为 ENTRY_QUERY_ID/WHOLE_PLAN_QUERY_ID，检索位置使用 SearchPhase 枚举；缓存初始桶数/装载因子、候选保护上限、能力发布状态和计划字段均已命名并注释。这些常量不改变实际检索时机、协议拼写、配置容量或数据库读取合同。两类生产代码的逻辑语句已补上方中文注释。

## 3. 数据库适配与当前实体合同

QdrantCapabilityRepository 不修改既有 persistence 模块。构造器接收 HttpClient、Config、文本嵌入函数、权威实体读取函数，例如 id -> store.read(明确的 Database, id)。数据库来源由装配方明确指定。

候选查询采用 Qdrant [Query points](https://api.qdrant.tech/api-reference/search/query-points/) 的 POST /collections/{collection}/points/query，携带有限 limit、score_threshold、with_payload 和 model/model_version 过滤。解析 result.points 中的 payload.entity，与现有 QdrantEntityStore 完整实体快照兼容。嵌入模型、版本、维数必须和集合一致。

目前支持的固化实体是 unitType=PLAN_STEP，data 合同为：

```json
{
  "publicationStatus": "PUBLISHED",
  "executionPlan": {
    "goal": "根据输入执行已审核任务",
    "steps": [
      {
        "id": "one",
        "goal": "查询指定日期订单",
        "kind": "TOOL",
        "toolName": "queryOrders",
        "arguments": {},
        "dependsOn": [],
        "bindings": {"date": {"source": "$input", "pointer": "/date"}}
      }
    ]
  }
}
```

以上 publicationStatus/executionPlan 是本适配器已实现的最小读取合同，不代表固化生成、审核或发布模块已实现。其他输入输出合同、范围、证据也可置于 data，供 Matcher 检查，当前没有通用自动审核实现。未修改 WorldEntity 类型或其字段。

索引仅提供候选；load 和 isAvailable 再读取权威实体，并检查发布状态及精确 revision。当前权威读取只支持当前实体，不假装能读取历史版本；要求版本和当前版本不同就拒绝。HTTP/读取故障向上传递，不用缓存默默冒充数据库已确认。

类型/发布状态当前在解析 payload.entity 后筛选；服务器侧按嵌入模型和版本过滤。共用集合可能被其他类型挤占候选，装配时优先使用按本模块合同维护的能力检索集合；不会擅自修改现有集合、创建发布数据或索引。若后续需要服务端类型/发布过滤，须与发布者同步建立可索引 payload 字段。

## 4. 两层缓存与新能力发现

PlanMatches 只属于一个 runId/planRevision，保存本次计划将用到的定义；下一次计划重新检索，不以旧匹配代替。内容缓存按 Ref 保存热点定义，容量与 TTL 在构造时指定，LRU 淘汰；参数属于本次运行，不写入共享定义。当前按条数限制，没有字节预算或并发加载合并。

每次 search 都调用 Repository.search。内容缓存只减少命中后的重复 load，不缓存“没有固化”，也不缓存永久允许执行。能力发布后无需广播全量更新；下次根入口或新 PLAN 的索引检索能发现已可检索的新版本。当前在途计划不会随发布静默替换。

候选搜索与执行资格检查是两类读取：前者发现能力，后者核对已经绑定的少量引用。执行前 isAvailable 仍可能访问数据库；缓存内容存在不等于状态可信。未实现可靠离线版本包或状态租约，因此数据库不可用时不能保证固化离线运行。

## 5. 已验证及后续工作

本地测试验证：入口只查一次；连续两次模型规划分别按总目标/子目标查询；入口未发现的子固化可在规划后找到并跳过子模型；固定内容缓存命中不阻止下一次搜索；缓存容量淘汰、停用重新检查、错误 revision 拒绝。本地 HTTP 服务器验证真实客户端的请求路径、嵌入目标、版本过滤、候选解析与权威加载。

尚未连接真实 Qdrant/Neo4j 或嵌入服务，未建立技能发布数据。后续按需增加：批量查询、历史版本库、索引发布/修复、加载合并、能力输出映射、受控语义/合同匹配策略。当前模块已可注入主流程，不能把端口和替身测试写成生产智能匹配策略已经完成。
