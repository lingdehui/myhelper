## 执行记录与恢复接线（2026-11-12）

`RunRecordAccess` 仅转交外部登记、领取、查询、事件和审核调用，保存本次运行的身份及领取凭据。它没有任务仓储、待办 Map 或业务回滚策略。`Handle.taskId` 是外部登记的稳定任务身份；`rootRunId` 每次 `submit/resume` 新建。未装配记录时 `taskId` 仅等于本次运行身份，`resume` 明确报错。

`PlanningContext` 在原七字段后增加 `taskId`、`phase` 和 `recovery`，旧构造仍兼容。每轮查询外部快照：`CONTINUE` 使用 `NORMAL`，`CONSULT_MODEL` 使用 `RECOVERY`，`WAIT` 返回 `Status.WAITING`。恢复阶段仍可提出普通计划，包括独立且获准的其他工作。模型返回 `COMPLETE` 时提交带快照版本的问题处理提案，外部 `review` 决定状态；循环不会因为模型写了“已解决”就删除问题。

工具实际派发前发送 `INTENT`，取得外部确认后才执行；收到结果后发送 `RETURNED`，验收后发送 `VERIFIED`。启用的记录端口发生故障不会静默退回内存继续执行。工具可以通过 `CallContext.reportBefore/reportAfter` 追加 `OBSERVED` 证据，具体版本、备份和差异由工具采集。模型调用失败发送 `MODEL_FAILED`；外部模块负责保留等待事项，应用之后调用 `resume(taskId)`。真实在途工作结束后才发送 `RUN_ENDED` 并结束领取，不跟随提前返回的取消结果释放。

上述为循环的端口和运行接线。2026-11-17 已由外部 records/application 实现持久提交、事件去重、单机进程所有权、待办状态及启动恢复；独立业务验收、影响核对和恢复工具仍需业务模块提供。恢复入口使用新运行的 `Limits`，尚未实现跨运行预算累计或旧 Future/计划游标重放，也不实现跨主机租约接管。完整合同见[记录与恢复端口](../records/28-执行记录与恢复端口开发文档.md)。

## 分支模型实现与代码阅读（2026-11-12）

1. `submit` 创建根运行、逻辑分支占位和 `RunModelAccess`，并将 `Planner.requirements()` 传入根运行合同。首次模型决策读取实际绑定时打开 `Session`。若入口整条固化包含模型工作，也可能先在混合计划分叉时打开会话。[AgentOrchestrator](../../../src/main/java/com/example/myhelper/orchestration/AgentOrchestrator.java) · [RunModelAccess](../../../src/main/java/com/example/myhelper/orchestration/RunModelAccess.java)
2. `executeModelPlan` 检查计划步数及工具白名单，再发起规划后检索。整条匹配时按照固化定义自己的计划决定是否需要模型路由。没有整条匹配时，按照原计划和命中的子节点能力决定是否校验原计划的路由。纯工具计划所有步骤沿用所在分支，依赖和参数绑定继续由 `TaskPlan` 校验。没有模型步骤的交叉 DAG 可以执行并跳过模型分配。[AgentOrchestrator](../../../src/main/java/com/example/myhelper/orchestration/AgentOrchestrator.java) · [PlanModelBindings](../../../src/main/java/com/example/myhelper/orchestration/PlanModelBindings.java)
3. 实际仍需模型的计划在派发步骤前分析分叉和汇合归属。线性和结构明确的 DAG 可以推导，归属有歧义时需要显式 `routing`。分析图会忽略传递冗余边，调度仍使用原 `dependsOn` 和参数绑定。布局校验失败会中止该次计划。[PlanBranches](../../../src/main/java/com/example/myhelper/orchestration/PlanBranches.java)
4. 依赖成功且参数绑定完成后，`PlanModelBindings.ready` 处理步骤归属。首次进入分叉时向 `Session` 整组申请子分支。局部汇合归还对应子组并沿用原父绑定。实际模型调用前按逻辑分支读取 `Binding`，再经 `PlanningContext` 和 `AgentCallerPlanner` 把 `modelRef` 交给 `AgentCaller`。[PlanModelBindings](../../../src/main/java/com/example/myhelper/orchestration/PlanModelBindings.java) · [单次调用](../agent/11-单次模型调用模块.md)
5. `CompletableFuture` 接续会等待实际步骤完成后回收计划内剩余的子分支。根工作收束后关闭已打开的 `Session` 并结束执行图。取消或超时可能先完成对外结果，在途调用结束后才触发上述清理。分支释放或根关闭异常会保留已取得的结果，以 `UNKNOWN` 报告并记录 `MODEL_SESSION`。已返回的取消结果保持原值，迟到的清理情况可查执行图。[AgentOrchestrator](../../../src/main/java/com/example/myhelper/orchestration/AgentOrchestrator.java) · [执行记录](13-执行链路记录开发文档.md)

`TaskPlan(goal, steps)` 和省略 `routing` 的 JSON 继续支持。可选 `routing` 的形状为 `{stepBranches: {stepId: branchId}, forks: [{id, parentBranchId, childBranchIds, joinStepId}]}`。本计划父分支使用 `$root`，`joinStepId` 为 `null` 表示计划末尾汇合。需要分析布局时，显式声明须覆盖全部步骤、分支层级无环、分支内线性且父分支在汇合前等待全部相关后代。内层汇合须在外层释放父绑定前完成。

八参数构造未装配可靠度查询，大多数含工具的固化会按未知评分回到模型路径并报告未装配。十二参数构造可注入可靠度门禁，评分满足时可免规划调用。依赖模型判断新参数范围时，可靠度模块仍会请求模型。九参数构造接收 `ModelAdapter`，可与 `AgentCaller` 共用同一个 `ConfiguredModelAdapter`。`Request.modelRef` 须为非空白引用。

检索可传 `CapabilitySearchPort.disabled()`，此时 `SEARCH` 节点记录 `enabled=false` 并返回空匹配。启用检索可使用 `CapabilityLookup`，检索异常沿工作链传播。根入口直接完成的纯工具固化无需打开模型会话。模型已经提交过 PLAN 的纯工具段沿用当前分支且不申请子模型，后续模型决策仍按结果继续。门禁与验收由装配方提供 `RuntimeGate`，原 `AgentOrchestrator.Checks` 实现继续可用。[运行门禁](../gate/15-门禁与验收开发文档.md)

`STEP` 节点记录 `branchId`、`parentBranchId`，`MODEL` 节点还记录实际 `modelRef` 和 `modelAssignment`。绑定登记是会话元数据操作，实际请求额度和服务并发控制待实施。固定提示、`routing` Schema 和反馈集中在 `LlmTexts`。

通过 `checks/run.ps1` 显式运行本地检查。循环接线及失败路径使用替身，`ConfiguredModelAdapterTest` 覆盖生产适配器的会话与引用回收。协议能力筛选和纯工具交叉 DAG 分别有 `ModelRequirementsTest` 与 `PureToolPlanTest`。实际运行记录和服务联调状态见接续文档。[检查说明](../../../checks/README.md) · [接续文档](../../重写架构与进度.md)

## 项目启动与 submit 调用现状

命令行由 `MyHelperApplication` 启动，`TaskRuntimeConfiguration` 装配编排器，`TaskEntry` 将文字转交 `submit`。业务工具、能力检索和持久任务记录由宿主按需提供。 [启动与装配](../deployment/21-装配部署与集成验收.md) · [交互入口](../interaction/20-交互与语音开发文档.md)

`AgentOrchestrator.submit(Request)` 接收新任务，返回异步的 `Handle.result`。装配记录模块后，可用 `resume(handle.taskId())` 接续已登记任务。`AgentCaller.call(Request)` 提供单次模型调用入口，外层循环由编排器驱动。

```text
MyHelperApplication.main
  → TaskRuntimeConfiguration 装配 AgentOrchestrator 和 TaskEntry
  → ConsoleInput 读取终端文字
  → TaskEntry.submit(text) 创建 Request 并调用 AgentOrchestrator.submit(request)
  → ConsoleInput 展示异步结果
```

独立检查用 `Harness` 装配替身并提交任务来验证编排行为。 [检查说明](../../../checks/README.md)

## 1. 实际调用链

```text
AgentOrchestrator.submit(Request)
  → 查询外部待处理事项（启用记录时）
  → 正常根入口：CapabilitySearchPort.searchAtEntry，最多一次
  → 整条匹配：检查适用、执行固化、验收，按结果返回或接续
  → 需要模型：runDecisionRound（执行一轮模型决策）
      → RunModelAccess：按需开启会话并读取本分支的 modelRef
      → AgentCallerPlanner.decide(context)
          → AgentCaller.call(request, scopedTools)，CALL_ONLY
          → 一次 ChatModel.call
          → 解析结构化 toolCalls，生成 Decision
      → PLAN：校验计划步数及工具，调用 searchAfterPlanning
          → 按实际替换后的计划判断是否需要模型分支
          → 命中固化步骤：直接执行固定版本
          → TOOL：SpringToolExecutor → ToolCallback
          → TASK：递归 task → runDecisionRound，不重复入口检索
          → SUCCESS / FAILED 汇总后进入下一轮模型
          → UNKNOWN 按外部待处理事项接续或返回
          → WAITING / CANCELLED / NEEDS_INPUT 返回
      → COMPLETE：普通阶段验收输出；恢复阶段提交结论给外部审核
      → NEEDS_INPUT：返回待补充信息
```

循环由 AgentOrchestrator 驱动；AgentCaller 始终只调用一次模型。计划由模型提出，代码负责校验、调度和保存执行事实。模型不操作 Java 线程。

## 2. 类型、工具调用与入参

模型可见两个控制工具，模型响应必须恰好包含一个工具请求：

| 原生工具名 | arguments | 解析结果 |
| --- | --- | --- |
| submit_plan | TaskPlan 的 JSON | DecisionKind.PLAN |
| finish_task | kind: COMPLETE / NEEDS_INPUT 和 output | 对应结束决策 |

判断工具请求来自 Spring AI 的 AssistantMessage.getToolCalls()，使用请求中的 id、name 和 arguments，不从自然语言里寻找“我要调用工具”。AgentCaller 在两种模式下均校验调用 ID 非空、不重复，以及工具名属于本轮允许集合。

`AgentCallerPlanner.requirements()` 声明 `TOOL_CALLING`。根运行的 `RunRequest.requirements` 将该协议能力传给 `ConfiguredModelAdapter`，用于筛选根模型和所有子分支的候选。普通工具白名单为空时，本协议仍使用 `submit_plan` 和 `finish_task`。白名单决定可执行的业务工具，协议要求决定可使用的模型配置。[模型适配器合同](../llm/27-模型适配器开发文档.md)

模型规划输入的 `task.toolReliability` 按工具调用名提供已知范围的历史统计。每个名称对应一个列表，每项包含 `rangeId`（已批准范围编号）、`score`（该范围内的估计成功率）、`successCount`（实际累计成功次数）和 `trustedAtomicTool`（当前实现的可信原子工具资格）。编排只为本轮白名单中已注册且能确定实际 `ToolRef` 的工具查询摘要。模型可见的是工具名和聚合字段，工具实现身份、历史参数及原始结果留在服务内。缺少工具或范围条目表示未知。

摘要用有限的只读查询获取同一实现和范围的已有证据，采集过程无需另行调用模型。模型可以用它参考选工具。实际派发仍依据绑定后的完整参数、实际工具身份及原有门禁判断，可靠度门限沿用本文“固化工具执行前的可靠度判断”一节。摘要中的历史估计无法确认本次参数落在该范围内。[统计口径](../skill/16-技能固化开发文档.md#17-2026-11-16-实际参数范围判断及归档消费接线)

编排适配器用 JSON Schema 告诉模型入参结构，再用 Jackson 转成 TaskPlan。类型决定代码分支，类型本身不理解用户意图。当前实现已用 switch(decision.kind()) 明确分发 PLAN、COMPLETE、NEEDS_INPUT；PLAN 交给 executeModelPlan，步骤再用 switch(step.kind()) 区分 TOOL/TASK。没有固定的“规划 → 执行模型 → 总结模型”三次调用。工具执行通常不调模型，总结可以由后续模型返回 finish_task.output。

原 loop 方法已改名 runDecisionRound，意思是“执行一轮决策”。switch 只负责选择本轮分支，轮次推进仍由计划完成后的异步回调再次调用 runDecisionRound。不能简单删除轮次接续，否则只会执行一次计划；也不应在工作线程内同步等待整棵子任务树。submit → task → runDecisionRound → executeModelPlan → executePlan 是建议阅读顺序；TOOL 动作的代码单独放在 executeToolStep。

## 固定值为什么存在

本轮按用户要求给新增核心代码的逻辑语句逐行补中文注释、展开压缩分支；字段注释仍放声明上方。保留以下区别，避免把所有字符串都当作业务魔法值：

| 固定值 | 当前表示及原因 |
| --- | --- |
| TASK、MODEL、TOOL、SPAWNED、RUNNING 等链路标签 | 改用 ExecutionTraceStore 的 NodeKind、EdgeKind、NodeStatus 枚举，防止任意拼写 |
| submit_plan、finish_task | 由 LlmTexts 保存，AgentCallerPlanner 引用，作为发给模型的工具协议名称 |
| $input、$entry、$plan | 提取为 TaskPlan/CapabilityLookup 的保留字常量，分别指任务输入、入口查询、整条计划查询 |
| 50ms | SpringToolExecutor.LOCK_CANCEL_CHECK_INTERVAL_MILLIS，是等锁期间检查取消的间隔，不是工具运行超时 |
| 16、0.75 | 内容缓存哈希表初始桶数/装载因子，已命名；真正缓存容量及 TTL 仍由构造器传入 |
| 1000 | MAX_CANDIDATES_PER_QUERY，是本地查询保护上限，不是 Qdrant 服务限制；实际候选数由 Config.limit 传入 |
| arguments、goal、status、result.points 等 | JSON/HTTP 协议字段，保留约定拼写并在代码旁解释；协议变更须同时修改读写方 |
| 0、1、~0、~1、HTTP 2xx | 分别涉及计数起点、版本规则、JSON Pointer 转义、HTTP 标准，按用途注释，不机械制造一批无意义常量 |

JSON Schema 和模型提示词是字符串内容，内部不能插入 Java 注释；在字符串定义上方解释用途，避免注释改变模型实际输入或破坏 JSON。

TaskPlan.Step 实际字段：id、goal、kind、toolName、arguments、dependsOn、bindings。kind 为 TOOL 或 TASK。例如模型调用 submit_plan 的参数：

```json
{
  "goal": "查询订单并生成报表",
  "steps": [
    {"id":"a","goal":"查询当天订单","kind":"TOOL","toolName":"queryOrders",
     "arguments":{"date":"2026-11-10"},"dependsOn":[],"bindings":{}},
    {"id":"b","goal":"根据订单生成报表","kind":"TOOL","toolName":"exportCsv",
     "arguments":{},"dependsOn":["a"],
     "bindings":{"rows":{"source":"a","pointer":"/rows"}}}
  ]
}
```

运行时先取 arguments 常量，再解析 bindings。source 为 $input 时读取本任务入参，其他 source 读取依赖步骤 Outcome.value；pointer 为 JSON Pointer。绑定结果覆盖同名常量。路径缺失或前驱不成功则不执行该步。解析后的 Map 序列化为 JSON，交给 ToolCallback.call(input, ToolContext)；工具自身负责业务参数校验。TaskPlan 校验不是完整 JSON Schema 校验器。

TASK 的入参传给递归子任务；运行身份和允许工具继承自运行时，模型不能任意指定父运行身份。

## 3. 检索与缓存时机

正常根 `submit` 最多进行一次入口检索，使用用户目标。外部有待处理事项时先按记录接续。`resume`、递归子任务和下一轮循环都跳过入口检索。

模型的 `PLAN` 通过结构、步数和工具白名单检查后，编排器调用一次 `searchAfterPlanning`。启用的 `CapabilityLookup` 先按计划总目标查询，再按各步骤目标分别查询。步骤查询携带原始 `Step`，供匹配策略核对工具名、类别和参数来源。`planRevision` 随轮次变化。`COMPLETE` 和 `NEEDS_INPUT` 直接进入各自的结果分支。

`PlanMatches` 保存本计划的整条/步骤匹配及不可变定义，`CapabilityLookup` 用有容量和 TTL 的固定版本缓存减少重复内容加载。每次执行选中的固化前，循环把能力版本、参数及恢复上下文交给 `CapabilityUsePort`。默认 `CheckedCapabilityUse` 检查发布状态和门禁，应用可以注入独立适用策略。见[固化检索](../capability/19-固化检索与缓存开发文档.md)。

匹配策略必须确认替换前后的输入、输出及副作用合同；不能仅靠同名工具或向量分数。当前组合执行输出为 stepId → {status,value,error}，没有自动输出字段映射器；不满足原步骤所需输出形状的能力不得替换。

## 4. 并发与失败

TaskPlan 校验步骤身份、依赖存在、数据绑定来源和 DAG 无环。就绪步骤提交给注入的 Executor；依赖通过 CompletableFuture.allOf(...).thenCompose(...) 唤醒。父任务不占线程同步等待子任务，因此一个工作线程也能完成递归任务。不同子任务可以同时调用模型；每个子任务自己的决策按轮顺序推进。同一计划收齐所有步骤结果后，再调用该父任务下一轮模型。

SpringToolExecutor.ResourceResolver 按本次参数解析实际资源，例如会话 ID、桌面、文件路径。相同资源经共享的条带锁串行执行，不同资源可并发；条带碰撞可能保守地串行。业务依赖来自模型/已有计划，资源互斥来自适配器掌握的真实资源，不使用注册工具时的固定“可并发”开关。跨任务需共用执行器实例才共享锁。

调用方管理工作池和计时器的生命周期、线程/队列容量；运行时另限制模型调用数、工具调用数、任务数、步骤数、每任务轮数、递归深度和总时限。当前没有按模型供应商分别限流。

后继只在所有前驱为 `SUCCESS` 时开始。计划按 `UNKNOWN`、`CANCELLED`、`WAITING`、`NEEDS_INPUT`、`FAILED`、`SUCCESS` 的顺序汇总。已知的计划结果和验收失败可进入下一轮，实际反馈随规划输入传递。动作或验收抛错可产生 `UNKNOWN`，此时只有外部返回 `CONSULT_MODEL` 才进入模型接续，返回 `WAIT` 则结束本次运行并报告 `WAITING`。启用任务记录时，模型调用失败会发送 `MODEL_FAILED` 事件并返回 `WAITING`。恢复阶段的 `COMPLETE` 交外部审核，普通阶段的 `COMPLETE` 仍交验收。持久幂等、动作影响核对和生产任务仓储待完成。[任务验收与恢复方案](../../planned/26-任务验收进度与断点恢复设计.md)

## 2026-11-12 结构化协议建议的解释（分析，未实施）

用户询问外部建议中的“协议思想可复用，具体名称未必通用”，以及 `type/version/stopCondition/confidence/idempotencyKey` 的含义。本次仅对照实际协议解释，不视为已批准字段扩展，也没有修改业务代码或运行新检查。

`submit_plan` 和 `finish_task` 是本项目向模型提供的两个控制工具名，合同在 `LlmTexts`；它们通过原生工具调用携带 JSON 参数。`AgentCallerPlanner` 使用 CALL_ONLY，随后解析成内部 `Decision(PLAN/COMPLETE/NEEDS_INPUT)`；实际业务执行仍由编排器接管。外部传输格式与内部调度类型已经分离，名称变更并不是实现这种分离的前提。

对方建议可以拆成三类：已有能力（结构化类型、目标、步骤和工具名/参数）；可评估的新合同（协议版本、完成条件、工具动作幂等）；尚无明确用途的字段（模型自报 confidence）。协议版本指 Schema 的版本，与当前 planRevision 的规划轮次不同。stopCondition 应先区分目标验收条件和运行时超时/预算限制，不能只添一句文字就宣称程序能检查。confidence 没有定义来源与校验方法时不能作为执行许可、验收或固化成功率。

`tool_request` 可作为解析绑定后交工具执行器的请求结构；当前 TOOL 步骤已有工具名与参数来源。不必因此增加第四种顶层模型决策，也不应绕过规划后检索、门禁、依赖和记录。idempotencyKey 若用于恢复/重试去重，应由运行时与独立记录/执行模块共同确定并保存，同一动作重试沿用，新动作使用新键；模型自填字符串或当前每次新建的 operationId 均不能单独保证业务幂等。接收方还须校验参数、保存回执并核对未知效果。

当前建议：保留两个控制工具及内部 Decision；协议版本和完成条件按消费者需求设计，业务幂等放入记录/执行合同联动开发；暂不为“主流化”新增 type 重复字段或 confidence。以上是本次分析建议，尚未确认实施。

## 2026-11-12 取得模型时记录具体任务

循环在 `invokeDecision` 取得本轮实际绑定后创建 MODEL 节点，并通过 TaskRecordPort 发送 MODEL_TASK_ASSIGNED；保存目标、参数、允许工具、模型引用、分支/父分支、分配来源、NORMAL/RECOVERY 和轮次。每轮节点身份是 callId，实际任务身份由 runId 关联，不能以 modelRef 为唯一键覆盖旧任务。

## 2026-11-15 固化工具执行前的可靠度判断（已接线）

范围是入口整条固化、规划后整条/子节点固化展开的 TOOL。模型新计划中明确给出的普通 TOOL 已经过模型决策，沿用原执行流程。单次 AgentCaller 不增加循环、评分或重规划职责。

```text
固化适用检查 → 等待依赖 → bind 完整工具入参 → 执行器解析固定工具身份
  → ToolReliabilityGate.evaluate(toolRef, arguments)
    → skill.ToolReliability.assess(toolRef, arguments)
    → 通过门限：原工具门禁 → INTENT → 派发时核对相同身份 → RETURNED → 验收
    → 缺少固定身份 / 未通过门限 / 无适用评分 / 查询异常：该动作不派发
      → 收集已有成功结果和拒绝原因 → 父任务下一轮模型判断并规划
      → 每次实际 PLAN 仍检索，但不再自动选中本根运行刚拒绝的技能版本
```

判断位于 AgentOrchestrator.executeReliableTool，分数来自技能模块，循环不实现公式、参数范围匹配或直接访问数据库。参数含本次常量、任务输入及已完成前驱输出；不在参数绑定前用空参数预判整条链。独立步骤仍并发，一个步骤评分不足不会撤销已经完成或在途的其他步骤。

ToolReliabilityGate 要求估计成功率严格高于 `myhelper.orchestration.direct-tool-reliability-threshold`（默认 0.85）。普通固化技能还需真实累计成功次数达到 `myhelper.orchestration.direct-tool-minimum-successes`（默认 5）。由当前版本权威工具目录确认的可信原子工具仅免次数要求。ToolReliabilityConfiguration 从 Spring Environment 读取两项配置并创建门禁 Bean。装配方提供 ToolReliability（内部 Lookup 由技能模块实现，经统一 persistence 查询），并把门禁 Bean 作为编排器第十二个参数传入。旧八至十一参数构造保留，但缺少评分查询时按未知交回模型；缺少 ModelAdapter 的旧八参数入口也就不能再无评分直执。

2026-11-17 新增的命令行装配可接收 `ToolReliabilityGate` Bean，默认使用不可用评分实现。生产固化直执还需装配实际业务工具、匹配和验收策略。 [启动与装配](../deployment/21-装配部署与集成验收.md)

低分结果是调度拒绝：Outcome.status=FAILED，value.executed=false，带 tool、arguments、reliability；并非工具实际执行失败，不发送该动作的 INTENT/RETURNED，也不增加工具调用计数。执行图 GATE 和记录端口 OBSERVED（phase=TOOL_RELIABILITY）保留分数、门限和原因。未启用记录端口时仅有本次内存图，不宣称持久保存。

被拒能力 Ref 的集合仅在当前 rootRunId 内用于阻止自动复用，既不修改发布状态，也不缓存评分。下次运行重新查询。每次模型 PLAN 仍按总目标和子目标检索，已拒版本保留候选参考但取消 selected。模型可以明确规划普通工具、选择别的能力或请求输入；原有白名单、业务门禁、预算、取消/指令版本检查与验收继续生效。高分只允许省略模型判断，不能越过这些检查。

技能模块已改用工具先验与实际样本加权的估计成功率，取值 0 到 1。普通技能与可信原子工具均应用同一分数门限。没有有效样本且无先验时交回模型。详见[技能固化](../skill/16-技能固化开发文档.md)。

已有成功步骤的结果交给模型继续使用，跨计划动作幂等仍待实现。回退模型不可用时保留已有结果，按模型失败路径返回。技能已有通过统一存储查实际参数和批准范围的生产组件，实际执行到持久归档的完整链和真实数据库、模型联调仍待完成。验证结果见[独立检查](../../../checks/README.md)。

## 2026-11-17 多链选择与失败后的接续

已接入一语义意图多条固定版本链的选择合同。入口一次、每次实际 PLAN 后的整条/子目标查询保持；执行前在既有候选内调用 `lookup.select(query, match, excluded)`，由 capability 核对本次参数、排序及加载。循环不计算链分，不修改技能发布状态。候选查询和评分在工作线程执行，不在等待依赖时阻塞父线程。已有业务门禁、工具来源、工具直执门限、预算、指令版本与结果验收继续生效。

依赖步骤等前驱真实完成后才绑定参数；选择 Query 里的 step.arguments 为完整实参，bindings 为空，不能拿参数字面部分冒充实际输入。选定链展开后的每个 TOOL 仍按自身绑定的参数通过工具可靠度门限。链分用于适用链的选择，不能替代工具直执许可。

候选失效或能力适用检查拒绝时，继续选本次召回中的下一个合格版本。执行器未实际派发时也可继续；判断来自宿主 `ToolDispatchGate.started`，不读取工具 value 中自称 executed=false 的任意字段。整个链的并发步骤收齐后，只要任一步已经派发，或进入了可能继续调用动作的 TASK，就不直接换整链重做。已有成功部分、执行失败和验收失败进入原有反馈；UNKNOWN 进入原有恢复核对，不直接尝试其他链。所有候选都不可用时保留拒绝原因，走原规划或反馈路径。

已确认 FAILED 的版本与完整参数记录在本根任务的 `CapabilityFailures`。后续 PLAN 仍检索，但同输入不再自动选该固定版本，其他输入不因普通执行失败全局失效。参数按 JSON 归一比较，忽略对象键顺序和整数 Java 宽度。原工具可靠度拒绝的本根版本集合仍按既有规则处理。此排除集合不跨进程持久化，跨重启效果核对仍依赖 records；不是业务动作幂等表。

模型路由依据最终执行的计划校验，不能在可用整链尚未选择前先因原计划汇合关系拒绝。已按纯工具建立的步骤布局在派发时只接受纯工具替换；迟到的含 TASK 候选跳过。若原 TASK 的纯工具替换失效且无替代，则给父模型 `CAPABILITY_ROUTING_REPLAN` 未执行反馈，不能偷偷在该布局加入模型分叉。原本为模型任务保留的分支仍可按既有规则执行。

新增 `CapabilityAlternativesTest` 使用单工作线程和实际编排器，检查候选切换、实际失败后先规划再选 B、未知效果不重做、成功部分保留、实参绑定以及纯工具替换失效后的模型路由。链展开、排序和部署接线条件见[19 当前实现](../capability/19-固化检索与缓存开发文档.md#2026-11-17-一意图多链的展开与可靠度选择)，验证结果见[checks](../../../checks/README.md)。
