## 1. 已确认并实现的检索时机

```text
一次根任务入口
  → searchAtEntry：按用户目标查数据库一次
  → 整条匹配并可执行：直接运行
  → 否则交给模型

每次模型提交 PLAN
  → searchAfterPlanning
      → 用模型计划 goal 查询整条固化
      → 用每个 Step.goal 分别查询子节点固化
  → 匹配合同、加载固定版本，保存 PlanMatches
  → 执行时绑定完整参数，在已有候选内重选，合格能力跳过额外模型规划

下一轮模型再次提交 PLAN
  → 再次执行上述规划后检索
```

正常新任务入口最多检索一次；`resume(taskId)` 和递归子任务进入模型循环，不重复根入口检索。COMPLETE、NEEDS_INPUT、等待前驱、工具回包不触发候选检索。固化定义展开也不是新模型规划，不重新做语义搜索。每次能力调用前另经 `CapabilityUsePort` 判断；兼容实现会调用 isAvailable 权威资格读取。

恢复接线：入口固化实际执行后 FAILED 会把反馈交给模型；确定未派发时可先尝试下一候选。UNKNOWN 只有在外部记录返回 CONSULT_MODEL 时才进入恢复判断，WAIT 则结束本次运行并报告 WAITING。检索本身不负责回滚，固化和普通工具共用执行事件合同。每次恢复 PLAN 仍重新检索，查询和适用端口均可收到问题上下文。2026-11-17 已增加本根运行同完整参数的失败固定版本排除；跨重启和业务影响判断仍归记录及恢复模块，不代表失败能力全局停用。具体见[记录与恢复端口](../records/28-执行记录与恢复端口开发文档.md)及[26 第 9 节](../../planned/26-任务验收进度与断点恢复设计.md#9-执行失败的影响记录优先处理与模型离线接续)。

## 2. 实际接口与职责

2026-11-12 用户确认并已接线：循环按约定时机检索，把固定能力版本、当前目标、已绑定参数和恢复上下文交 `CapabilityUsePort.evaluate(UseRequest)`，按 `UseDecision(usable, reason)` 执行或拒绝。独立适用模块负责判断，循环不解释失败影响或根据语义分数自动放行。

`CheckedCapabilityUse` 是兼容实现，先查 `search.isAvailable(ref)`，再调用 `RuntimeGate.allow(...)`。编排器可注入业务适用实现。默认适用判断不解释恢复事项，输入及输出合同由 Matcher 核对，业务状态和效果核对由已装配的门禁与恢复策略提供。 [兼容适用实现](../../../src/main/java/com/example/myhelper/capability/CheckedCapabilityUse.java)

`CapabilitySearchPort` 提供携带 `Map<String,Object> context` 的入口和规划后重载。循环传入包含 taskId、rootRunId、runId 和 recovery 的不可变快照。兼容重载委托旧方法。当前根运行内确认失败的固定版本由循环按相同完整参数传给 `select` 排除。根据任务归档解释跨运行恢复上下文仍需要业务检索或适用策略。 [兼容端口](../../../src/main/java/com/example/myhelper/capability/CapabilitySearchPort.java) · [同次运行排除](../orchestration/12-并行分支循环编排设计.md#2026-11-17-多链选择与失败后的接续)

| 代码 | 已实现职责 |
| --- | --- |
| CapabilitySearchPort | 入口/规划后查询及其上下文重载；select 在已召回候选内按实参及排除集合重选；disabled 明确未启用，故障不伪装为空候选 |
| CapabilityUsePort | evaluate(UseRequest)，返回本次固定能力版本可用性及原因 |
| CheckedCapabilityUse | 兼容已有权威发布状态与门禁检查；不自动解释恢复上下文 |
| CapabilityLookup | searchAtEntry、searchAfterPlanning、select、isAvailable、cachedCount；组合业务匹配和技能链分，维护有界定义缓存 |
| Repository | search(Query)、load(Ref)、isAvailable(Ref) |
| Matcher | matches(Query,Candidate)，必须由业务装配，不默认按分数放行 |
| QdrantCapabilityRepository | 调用统一存储获取向量候选和权威实体，核对固定 revision 和发布状态；不创建 HTTP 客户端 |
| PlanMatches | 本次计划整条及 stepId 到 Match 的映射，由计划执行链持有 |
| 内容缓存 | Lookup 内部有限 LRU + TTL，按 namespace/id/revision 保存不可变 Definition |

Query 包含 runId、planRevision、stepId、goal、arguments、可选原始 Step。入口 stepId 为 $entry，整条为 $plan。子节点查询携带模型给出的工具名、类别、参数和绑定来源；未知上游结果不伪造为已知参数。实际检索文本来自 goal。

Candidate 包含固定 Ref、description、contract、semanticScore；旧三参构造缺省语义分为 0。Match 保留本次候选和可选的已选 Definition；Definition 为固定 Ref + TaskPlan。匹配器负责确认目标、输入/输出形状、作用范围和副作用等价。名称相同或语义相近不足以替换；无法确认时返回 false。执行阶段仍以实际绑定参数经过独立适用判断和结果验收。

当前组合输出为 stepId → {status,value,error}，没有额外输出映射字段；匹配器必须确保调用方能消费该形状。通用能力参数适配、分支条件、历史版本加载、依赖批量展开仍未实现。

可读性整理：$entry/$plan 提取为 ENTRY_QUERY_ID/WHOLE_PLAN_QUERY_ID，检索位置使用 SearchPhase 枚举；缓存初始桶数/装载因子、候选保护上限、能力发布状态和计划字段均已命名并注释。这些常量不改变实际检索时机、协议拼写、配置容量或数据库读取合同。两类生产代码的逻辑语句已补上方中文注释。

## 3. 数据库适配与当前实体合同

2026-11-13 用户确认所有数据库查询和保存均经过 persistence。`QdrantCapabilityRepository` 已改为 `new QdrantCapabilityRepository(store, config, embed)`，其中 store 是通过 `PersistenceConfiguration`/`application.yml` 装配的共享 `DualWriteStore`；不再传 HttpClient、URI、集合名、密钥或任意读取回调。`Config(namespace, authoritativeSource, embeddingModel, embeddingVersion, dimensions, limit, scoreThreshold)` 只保留能力合同和明确的权威读取来源。旧构造签名已移除，项目内检查调用已同步。

2026-11-16 新增生产入口 `QdrantCapabilityRepository.withTextEmbedding(store, searchConfig, embedding)` 与 Spring [CapabilityRepositoryConfiguration](../../../src/main/java/com/example/myhelper/capability/CapabilityRepositoryConfiguration.java)。嵌入使用技能发布共用的 `textEmbedding`，从实际返回值获取模型及版本；仓储装配时无需查询 Ollama。召回维数沿用 `qdrant.vector-size`，权威库沿用 `myhelper.skill.authority`（默认 NEO4J）。命名空间默认取 `qdrant.collection`，可由 `myhelper.capability.namespace` 覆盖。`myhelper.capability.limit` 默认 20，`myhelper.capability.score-threshold` 默认 0.0，两者只作用于召回。既有接收 float 向量和显式版本的构造仍可用。

候选通过 `store.search(QDRANT, VectorRequest)` 查询；实际 HTTP、认证、超时、有限数量、模型/版本过滤、协议检查与完整实体还原由 `QdrantEntityStore` 执行。能力仓储在向量候选限额生效前筛选 `/unitType` 为 `PLAN_STEP` 或 `INTENT` 且 `/data/publicationStatus` 为 `PUBLISHED` 的点。随后通过一次 `store.readBatch(config.authoritativeSource(), ids)` 核对类型、修订和发布状态。旧链直接形成候选，INTENT 通过 Neo4j 的 `data.intentId` 条件查询批量分页展开链，以链的权威实体生成候选描述和合同，保留召回语义分。选择顺序由 Lookup 的适用匹配及链分排序决定。`load`、`isAvailable` 使用 `store.read(config.authoritativeSource(), id)`。嵌入模型、版本、维数必须和存储配置的集合一致。完整查询合同见[统一存储](../persistence/10-统一双写模块分析.md)。

已写入 `payload.query_terms` 的数据可直接使用筛选。历史点没有投影时仍可按 ID 读取，部署前按统一存储的旧数据升级方式分页重写 Qdrant 点以参加候选查询。查询过程不改库，也不自动放宽索引筛选。过期指索引修订与权威实体不一致，或权威实体已停用、缺失。定时有效期字段、索引对账重建与跨库发布保证另行实现。

可执行固化实体仍是 unitType=PLAN_STEP。关联意图时在 data 增加 intentId；INTENT 本身提供语义入口，不作为可执行计划。链的最小 data 合同为：

```json
{
  "publicationStatus": "PUBLISHED",
  "executionPlan": {
    "goal": "根据输入执行已审核任务",
    "steps": [
      {
        "id": "one",
        "goal": "查询指定日期订单",
        "kind": "TOOL",
        "toolName": "queryOrders",
        "arguments": {},
        "dependsOn": [],
        "bindings": {"date": {"source": "$input", "pointer": "/date"}}
      }
    ]
  }
}
```

以上 `publicationStatus` 和 `executionPlan` 是本适配器读取可执行链的最小合同。输入输出合同、范围和证据交由业务 Matcher 检查。技能模块已支持候选生成、接收审核决定及按决定发布单链或归组链。通用自动审核和从归档自动提取新候选仍待接入。 [技能发布与链分](../skill/16-技能固化开发文档.md#18-2026-11-18-一意图多链发布与归档评分)

索引仅提供候选；批量读取、load 和 isAvailable 比较权威发布状态及精确 revision。若候选在匹配与加载间失效，Lookup 移除该候选并检查下一项；全部落空时按原路径继续规划。仓储返回另一个修订、连接失败、响应协议错误仍报错。定义缓存继续按固定引用保存，执行前重新读取资格。历史修订的独立保存和读取仍待实现。

当前向量请求已使用服务端类型和发布状态条件，同时按嵌入模型及版本过滤，返回后仍核对权威实体。旧记录需具备 query_terms 投影才能参与这些条件查询。生产数据升级与集合选择由装配方明确处理，不能绕过存储模块另建客户端；本次多链展开不会自动迁移或重写旧点。

## 4. 两层缓存与新能力发现

PlanMatches 只属于一个 runId/planRevision，保存本次计划将用到的定义；下一次计划重新检索，不以旧匹配代替。内容缓存按 Ref 保存热点定义，容量与 TTL 在构造时指定，LRU 淘汰；参数属于本次运行，不写入共享定义。当前按条数限制，没有字节预算或并发加载合并。

每次 search 都调用 Repository.search。内容缓存只减少命中后的重复 load，不缓存“没有固化”，也不缓存永久允许执行。能力发布后无需广播全量更新；下次根入口或新 PLAN 的索引检索能发现已可检索的新版本。当前在途计划不会随发布静默替换。

候选搜索与执行资格检查是两类读取：前者发现能力，后者核对已经绑定的少量引用。执行前 isAvailable 仍可能访问数据库；缓存内容存在不等于状态可信。未实现可靠离线版本包或状态租约，因此数据库不可用时不能保证固化离线运行。

## 2026-11-17 一意图多链的展开与可靠度选择

本节为已实现的检索及选择路径，正文接口和存储合同已同步。发布归组、实际链级证据和评分实现归技能模块，不由检索模块生成。

Qdrant 查询先按相同嵌入版本和 `publicationStatus=PUBLISHED` 召回 `INTENT` 或旧的 `PLAN_STEP`。索引结果批量回源并核对同类型、同修订和发布状态。多个有效 INTENT 的 ID 合并成一次 `data.intentId IN (...)` 条件查询，在 Neo4j 分页展开已发布且具有 executionPlan 的链。关联链用自身 ID/revision，不要求与意图版本相等。旧直接索引和意图展开重复召回同一 Ref 时去重，保留最高语义分。此读取路径不写入或重嵌入意图。

每页最多 100 条，单次展开读取预算 1000；达到上限仍有后页就明确报告超限，不把截断结果称为最高可靠度。新意图路径要求权威来源为 Neo4j，其他来源配置继续支持旧的直接链检索，遇新 INTENT 明确拒绝。所有读操作经 `DualWriteStore`，不另建数据库客户端。

`Candidate(ref, description, contract, semanticScore)` 保留旧三参构造，缺省语义分为 0。`CapabilityLookup` 先剔除停用或固定版本失效的引用，调用宿主 Matcher 核对目标合同和本次参数范围，再通过 `SkillChainReliability.score(skillId, revision, arguments)` 读取链级分数。排序为：有证据先于未知 → 链分降序 → 语义分降序 → namespace/ID/revision 稳定次序。空或不合法分数作为未知，读取异常向上报告；不从普通工具成功率推算链可靠度。范围不符候选只能作为模型参考，不成为 selected。

`CapabilitySearchPort.select(Query, Match, Set<Ref> excluded)` 在已经召回的候选内重新匹配、查分和选择，不再次请求向量检索。根入口及每次实际 PLAN 后仍按原时机查库。含未解析 bindings 的步骤只保留候选，不按残缺参数匹配或评分；执行前依赖完成后，循环传入完整参数和清空 bindings 的本次 Step，再选择链。缓存仍只存固定定义，不缓存分数和执行资格。旧端口默认 select 仅复核它原先已选的定义，不擅自把候选升级为可执行。

宿主显式导入 `CapabilityRepositoryConfiguration` 且提供 `CapabilityLookup.Matcher` 时，可装配 Lookup。已有自定义 SearchPort 优先。缓存配置为 `myhelper.capability.cache-capacity`（默认 256）和 `myhelper.capability.cache-ttl`（默认 5 分钟）。技能模块的 `SkillRuntimeConfiguration` 已导入链分提供方和归档消费组件，发布仓储由 `SkillRepositoryConfiguration` 提供。配置可选链分 Bean，缺省将分数标记为未知。正式 `main` 未导入能力检索和技能配置，应用缺端口时关闭检索。因此组件检查和正式启动的部署状态分别验收。 [检索装配](../../../src/main/java/com/example/myhelper/capability/CapabilityRepositoryConfiguration.java#L24) · [链分装配](../../../src/main/java/com/example/myhelper/skill/SkillRuntimeConfiguration.java#L18) · [运行时缺省](../../../src/main/java/com/example/myhelper/interaction/TaskRuntimeConfiguration.java#L144)
