## 应用启动链路

1. **Java 入口**是 [MyHelperApplication.main](../../../src/main/java/com/example/myhelper/MyHelperApplication.java)。在 IDE 中直接运行该启动类。使用 `java -jar` 时，JAR 清单中的 `Main-Class` 指向 Spring Boot 的 `JarLauncher`，它再调用 `Start-Class` 指定的 `MyHelperApplication.main`。命令见[项目 README](../../../README.md#启动命令行)。
2. **Spring Boot 装配应用。** `main` 以 `WebApplicationType.NONE` 创建容器，显式导入模型、任务运行、持久恢复、世界模型与设备工具配置。任务持久化与启动恢复默认启用，启动时会访问 Neo4j。容器启动后默认运行 `ConsoleInput`，传 `--myhelper.ui=desktop` 则打开 Swing。两种模式都由 `main` 管理容器寿命。 [启动类](../../../src/main/java/com/example/myhelper/MyHelperApplication.java) · [装配与切换](../deployment/21-装配部署与集成验收.md)
3. **两种界面提交同一种文字任务。** 终端与 Swing 调用 `TaskEntry.submit(text)`，该入口保留任务原文并交给 `AgentOrchestrator.submit(request)`。编排器需要模型决策时，经 `AgentCallerPlanner` 和 `AgentCaller` 调用 Spring AI 的 `OpenAiChatModel`。模型地址、密钥和模型名称沿用 `spring.ai.openai` 配置。 [任务入口](../../../src/main/java/com/example/myhelper/interaction/TaskEntry.java) · [模型配置](../../../src/main/java/com/example/myhelper/llm/ModelClientConfiguration.java)

## 已实现的文字入口

- 启动时默认装配异步任务日志。装配 `RunArchivePort` 时，终端通过 `/history <taskId> <rootRunId>` 查看已提交的运行归档。命令使用日志中的 `task=` 和 `root=`，实时进度可与最终结果交错出现。 [任务日志](../tasklog/任务日志开发文档.md)
- [ConsoleInput](../../../src/main/java/com/example/myhelper/interaction/ConsoleInput.java) 逐行读入文字，空行跳过，各行独立提交。终端按运行 ID 输出状态、结果及错误，包括 `NEEDS_INPUT` 及其问题。输入 `/exit` 或读到 EOF 后等待已提交任务的对外结果。
- [TaskEntry.submit(String)](../../../src/main/java/com/example/myhelper/interaction/TaskEntry.java) 保留文字原文，构造根任务并转交 `AgentOrchestrator.submit`。返回的 `Handle` 提供任务 ID、运行 ID、异步结果、取消请求和实际收尾信号。应用关闭时停止受理，向未收尾任务请求停止并有界等待。
- [Swing 桌面调试入口](31-Swing桌面调试界面开发文档.md)通过同一个 `TaskEntry` 提交新任务，按任务显示气泡、任务树、时间线和对话结果。已受理的运行可在详情发出取消请求。

## 运行中接入语音

语音模块获得正在运行的 `TaskEntry` 实例后，将每条最终转写交给 `submit(text)`，并通过返回的 `Handle` 获取结果。ASR 可以在自己的线程接入或停止，终端与语音共享后端。识别临时片段、收音、去重、播放和设备管理由语音模块负责。当前交付范围是同进程提交接口，语音插件发现和加载器留待语音实现。

命令行当前以提交新任务和查询归档为主，Swing 已能对受理的运行发出取消。将语音识别的文本关联到已有 `taskId`、接入修改，以及把 `NEEDS_INPUT` 的回答交回原任务，属后续交互接线。 [指令与恢复合同](../records/28-执行记录与恢复端口开发文档.md)

## 后续交互合同

文字、语音或其他入口统一产生 UserInstruction：commandId（原建议 instructionId，语义为一次输入的去重身份）、sessionId、关联 taskId、观察到的 rootRunId（可选）、正文、时间、来源、预期指令版本和明确的新增/修改/暂停/取消标记（若入口能提供）。恢复沿用稳定 taskId，不能只靠会变化的 rootRunId 找原任务。输出消费运行事件和最终结果，展示等待用户、执行中、部分失败和取消。

入口不自行拆自然语言任务；把指令交给[编排器](../orchestration/12-并行分支循环编排设计.md)。多条同时到达的指令允许并行，不用一条全局聊天消息列表承载所有任务。指代及业务先后由模型或明确入口关系解析。

## 语音流水线

音频采集 → VAD/分段 → ASR → 语句组装 → 统一指令入口；输出经文本事件 → TTS → 播放。唤醒、声纹、设备选择作为入口策略，优先恢复文字入口再接音频。旧资源路径、模型许可与兼容性实施时核对。

## 打断与追加

停止播音不等于取消工具；取消任务必须带稳定任务身份，定向取消某次运行时另带 rootRunId。用户追加要求更新受影响任务版本，无法确定指代时询问；不能把所有新发言当作取消前一任务。事件去重避免一次语音被重复提交。模型等待用户时保留关联信息，补充回复只恢复对应任务。

2026-11-12 用户确认先补设计。对明确关联原任务的“打断并修改”，应用鉴权后向记录模块持久提交 commandId、taskId、expectedInstructionRevision 和正文；同 ID 重试不重复接收，版本冲突不静默覆盖。入口不要求用户持有工作线程或 RunClaim。正文和指令顺序完整保存，由模型结合旧目标、已做事项和影响判断如何调整。

首版建议停止该任务的新派发，保存旧在途结果，旧运行真实结束后以同一 taskId 创建新运行并重新规划。应用分别展示“新指令已接收”“旧运行正在收束”“新要求已纳入计划”，不把取消 Future 当作工具已停止。暂停等待继续，取消不自动恢复原目标；独立新任务可另行并发。模型暂时不可用时，新指令及已有修改仍保留，待恢复入口接续。

`resume` 加载原 `TaskSpec` 后绑定最新指令，模型收到原目标、按序输入及记录模块提供的进度。编排器已提供 `instruct`、`amend` 和 `resume`，记录模块已实现正式持久仓储。暂停后可提交 `CONTINUE`，待旧运行实际收尾后显式 `resume`。界面侧还缺任务关联、用户鉴权及修改、继续和关联回答入口。 [完整设计](../../planned/26-任务验收进度与断点恢复设计.md#10-中断记录启动恢复与追加指令重新规划) · [记录与启动恢复](../records/28-执行记录与恢复端口开发文档.md#13-2026-11-17-正式持久任务与启动恢复已实现)

## 验收

相同指令 ID 不重复执行；同时指令不串上下文；打断播音与取消执行分开；音频失败可以报告或回退文字；长任务持续显示真实进度；最终回复能关联执行证据；语音链路单独验证，不以资源文件存在代替可运行。
