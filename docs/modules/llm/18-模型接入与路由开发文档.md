## 职责与合同

外部 ModelAdapter 的 Session 维护一个根运行内的真实绑定，按下文规则选择模型、登记父子分支、回收绑定；resolve 将最终 modelRef 解析成 ChatModel。候选列表、模型筛选和引用计数均由适配器实现，不再返回循环侧进行二次分配。循环负责分支拓扑、发起绑定需求、使用结果及结束通知；单次模块按最终引用调用一次。每轮重新按任务类别择模不能覆盖线性沿用与汇合恢复规则。密钥留在适配器配置中，不进入世界模型、执行链路或提示词。

当前 `RunRequest` 包含 `rootRunId`、`rootBranchId`、`modelRef`、`toolNames` 和 `requirements`。`AgentCallerPlanner` 始终声明 `TOOL_CALLING`，适配器用同一要求筛选根模型及分叉候选。四参数兼容构造默认要求 `TOOL_CALLING`。`fork` 接收父绑定和有序子身份。调用用途、上下文额度、降级范围、调用身份和统一用量仍为后续建议。见[模型适配器合同](27-模型适配器开发文档.md)。

循环现在通过 `PlanningContext.phase` 区分 NORMAL/RECOVERY，并携带外部记录快照；这是规划上下文，不改变模型适配器的分配规则。模型故障的事件发送和 `resume(taskId)` 接续已接线，持久待办、恢复领取和业务结论审核由独立记录模块负责。适配器不存储等待模型队列，也不决定是否回滚。[记录与恢复端口](../records/28-执行记录与恢复端口开发文档.md)

## 与单次调用的边界

单次调用仍只请求一次模型；轮次和跨模型重试由编排器决定。配置禁用框架隐式工具循环，按项目锁定的 Java 25 / Spring AI 2.0.0-M3 核对本地 API。不能根据最新在线示例自动升级依赖。

多个独立任务可并发调用模型；设置按提供方、模型和全局的在途数限制及排队时限。具体 ChatModel/客户端线程安全性在适配时验证，不能仅因 AgentCaller 无可变消息字段就假定所有依赖可并发。

## 错误与用量

区分网络/限流、认证配置、上下文超长、响应截断、协议错误及模型拒绝。只在上层明确策略下重试，保留每次请求身份；工具执行结果不因切模型被重放。用量未知标未知，不能用零替代；记录模型耗时与等待耗时，评估并发是否真的缩短关键路径。

## 验收

modelRef 可准确解析；能力不匹配不调度；单次调用不隐式递归；工具参数协议保留；限流排队有界；用量/模型版本可追踪；模型切换保留正确消息；没有真实服务验证时仅报告模拟/接口验证。

## 2026-11-12 分支模型分配规则（用户确认）

模型绑定在运行分支上。一条线性路径包括多次规划、工具执行和修复，继续使用同一个模型；出现并行子分支时，给子分支分配其他可用模型。父分支保留原模型，等这组子分支汇合后继续。子分支再次分叉时递归应用同一规则。

```text
A 规划并沿主线执行
  ├─ B 分支
  │    ├─ D 分支
  │    └─ E 分支
  │    D/E 汇合 → 回到 B 继续
  └─ C 分支
  B/C 汇合 → 回到 A 继续
```

用户进一步明确：模型不足时，能分配多少就分配多少，其余沿用父模型。例如只有 A、B 时，A 分成两支，分别使用 B、A；只有 A 时，两支都使用 A。不能因为没有足够新模型而拒绝分叉或等待配置增加。模型引用相同也不代表两个分支共享消息。

### 分配与执行规则

| 情况 | 规则 |
|---|---|
| 根任务 | 使用调用方指定的初始 modelRef；若应用需要选择默认模型，由应用/目录配置提供 |
| 线性下一步、重新规划、单个 TASK 递归 | 沿用当前分支模型；递归本身不等于分叉 |
| 真正的并行分叉 | 为各子分支选其他可用模型，不覆盖父绑定 |
| 其他模型不足 | 逐个分配可用模型，剩余子分支继承父 modelRef |
| 嵌套分叉汇合 | 回到这一组分叉的父分支及原模型，不直接回根模型 |
| 根分叉汇合 | 回到根分支及原模型 |
| 普通工具或无需模型的固化执行 | 直接执行，不能为了模型分配而额外调用 LLM |
| 同一分支需要模型验收 | 可沿用分支模型，但使用独立的验收请求与证据；调用用途本身不触发换模型 |

“等待”是保存父分支状态并注册异步接续；不占住工作线程或模型请求并发名额。父分支已有的请求结束后释放请求许可，随后才等待子分支。子分支共用父 modelRef 时仍保持各自的目标、上下文、进度与证据；实际请求是否同时运行受模型服务额度约束。

### 当前接口与运行状态边界

| 组件 | 所属与职责 |
|---|---|
| `ModelAdapter` | 模型接入接口；`ConfiguredModelAdapter` 实现 `openRun`、`resolve` 及 `Function<String, ChatModel>` |
| `ModelAdapter.Session` | 外部维护根绑定、活动绑定、整组分配、模型引用计数、释放与关闭；接口包含 root/binding/fork/release/close |
| `RunModelAccess` | 循环侧只做按需打开、返回合同校验和关闭，不筛选候选、不计数 |
| `PlanModelBindings` | 循环侧只保存返回 Binding 与本计划 scope/fork 的关联，按依赖结束通知外部释放 |
| `PlanBranches.Layout/Fork` | 循环侧维护控制拓扑、步骤归属及汇合边界，不决定具体模型 |
| 步骤归属表 | 循环侧维护：按计划修订和 stepId 映射 branchId，不能仅用模型名作为分支身份 |
| 单次调用 | 接收已选好的 modelRef，请求一次；不枚举分支、不分配模型、不持有整棵任务状态 |

`ConfiguredModelAdapter` 在同一根任务内按子分支顺序，优先选用外部标签画像推荐的空闲兼容模型，再按配置顺序回退。保留父绑定，兼容候选耗尽时继承。`Session.fork` 整组登记并按请求顺序返回，活动中的同批申请可重放。`Session.release` 处理已结束的子分支，根绑定在会话关闭时回收。

逻辑分配范围与实际请求限额分开：不同根任务可使用相同模型引用，模型接入层约束实际并发。不因某模型暂时占满请求额度就擅自改变分支绑定；排队、超时或失败按任务策略处理。父模型被禁用或不再支持请求时也不能强行调用，需明确返回不可用或由上层显式决定变更，不能暗中改成每轮轮询模型。

### DAG 汇合与上下文

现有 `TaskPlan.dependsOn` 表达执行和数据依赖，不总能唯一推导分叉归属。PlanBranches 已支持结构明确的 DAG 自动分析，歧义图通过 TaskPlan.routing 明确分支及 fork/join 边界。一个节点可能只汇合部分支线，也可能只是读取另一支线的数据；跨支数据依赖不自动结束分支或切模型。循环负责这些控制结构，外部模型适配器收到经校验的分叉身份后再完成实际分配。

同一运行中的父分支接续时使用自己的上下文，加上相关子分支结果及验收依据；不依赖模型服务端自动记住对话，也不把所有子分支完整聊天拼接起来。跨运行 `resume(taskId)` 当前从外部读取原目标和问题，生成新 rootRunId，按原配置引用按需打开新 Session，再让模型判断如何继续。它不复活旧 Session、线程或 Future，也尚未实现原分叉游标和预算的持久重放。若未来需要恢复原控制拓扑，应在独立记录合同中明确保存与重建规则。

### 当前实际实现及交付边界

编排器通过 `RunModelAccess` 按需打开根会话，将实际绑定的 `modelRef` 经 `PlanningContext`、`AgentCallerPlanner` 交给 `AgentCaller.Request`。装配方可把同一个 `ConfiguredModelAdapter` 直接作为单次调用的解析函数和编排器的模型端口。

九参数编排器构造显式传入 `ModelAdapter`。八参数构造可执行根入口直接命中的纯工具固化，进入模型路径时报告未装配。编排器根据能力替换和递归展开后的实际计划判断是否需要模型。纯工具计划沿用计划所有者的分支，依赖按 DAG 调度，无需分析模型路由或申请子绑定。仍需模型的计划保留 `PlanBranches` 布局校验，分叉时整组登记真实绑定。

实际工作结束后关闭会话，取消回执可以先返回；记录模块的运行结束通知也等待真实工作收束。循环接线、生产适配器分配及协议筛选已有本地检查。实际进入规划模型后失败且任务记录已启用时，循环报告 MODEL_FAILED，记录接受后返回 WAITING，由外部保留待办；预算、取消、装配和调度失败不冒充模型故障。模型模块本身不会重放工具。供应商联调、底层请求取消及生产持久恢复仍待完成。见[主流程说明](../orchestration/12-并行分支循环编排设计.md)、[记录与恢复端口](../records/28-执行记录与恢复端口开发文档.md)和[检查记录](../../../checks/README.md)。

## 模型适配器与公共变量查询（2026-11-12 分析建议）

用户询问是否通过模型适配器，根据公共变量中的线程 ID 找到模型 ID。建议补齐真实模型配置的注册/解析实现，复用现有接口；若“线程”指逻辑任务分支，对应 branchId；不要用 Thread.currentThread 的工作线程 ID 或 ThreadLocal 决定业务模型。当前 CompletableFuture 调度下，同一分支的后续动作可能由其他工作线程接续，一个工作线程也可能先后处理多个分支。

两层映射由独立适配器维护。会话保存 `branchId → Binding(modelRef, parentId, assignment)`，`resolve` 提供 `modelRef → ChatModel`。 `modelRef` 是配置连接引用。 `AgentCaller` 通过注入的解析函数使用该引用。

外部模块若需通过公共变量入口查询当前绑定，可由模型适配器提供按 rootRunId、branchId 查询的只读视图；目前尚无跨任务查询服务或 ToolVariables 接入。权威绑定保存在外部 Session，公共变量不复制可写绑定表、不提供全应用 currentModelId。循环只按生命周期发起申请和释放；选择、状态更新及资源回收由适配器完成。Session 关闭后的历史查询应转向执行记录。

调用路径为“会话返回绑定 → 请求携带 `modelRef` → `AgentCaller` 解析并调用一次”。生产适配器已实现配置解析和分支分配，跨运行的公共变量读视图仍为建议。见[模型适配器](27-模型适配器开发文档.md)。

## 2026-11-12 多供应商、多账号与延迟路由分析（未实施）

用户询问按近期延迟选模型、前缀/语义缓存和减少串行轮次是否适用于当前多供应商或同供应商多账号设计。本轮为源码及官方资料核对，没有变更已确认的分支绑定策略，也没有实现动态路由、结果缓存或请求配额。

当前 `ConfiguredModelAdapter.ModelConfig.modelRef` 标识一份已配置客户端连接，不要求它等于供应商模型名称。因此装配方可以为同一模型的不同账号分别提供客户端和不同 modelRef。适配器按画像偏好和配置顺序选择本根运行尚未占用的兼容引用，不能由引用不同推断底层额度或缓存互相独立；跨根任务也没有全局请求许可和队列控制。

需要区分三个问题：任务分支可以并发；某个请求选择哪份连接；连接受哪个组织/项目/部署额度限制。多供应商可能提供不同的可用容量，同供应商多个账号也可能有独立额度，但多个密钥不保证多个独立配额。例如 Claude API 的组织级总限制仍生效，workspace 可设更低限制。是否能减少排队应按实际限额归属验证。[Claude 限流说明](https://platform.claude.com/docs/en/api/rate-limits)

延迟路由是一种可选优化，不等于同一分支必须每轮换不同模型。LiteLLM 同时提供近期延迟选择和会话固定路由，统计 TTL 可配置，因此“5–15 分钟滑窗”不是通用协议。比较候选需要先满足任务能力和输出合同，再区分排队耗时、完整响应耗时、输入/输出长度、失败与重试。当前规划器等待完整控制工具参数，不能只看首 token 时间。按历史平均值选中同一连接也可能把新的并发请求集中排队，需结合在途负载和额度。[路由策略](https://docs.litellm.ai/docs/router/learn/strategies) · [会话固定与 TTL 配置](https://docs.litellm.ai/docs/routing)

候选改进建议是先保留分支身份及父子汇合规则，在新分支分配时根据观测到的负载、延迟和能力排序；已有分支默认保持绑定。同一模型、兼容参数与合同下的多个连接可另设请求级路由，但要显式区分逻辑模型和实际连接身份、记录实际选择，并评估缓存重用。跨模型变更须单独定义策略，不能暗中覆盖用户已确认的固定绑定。以上尚未确认实施。

缓存需要分开看：前缀缓存复用输入计算，命中后仍发模型请求并生成输出；结果/语义缓存复用已有回答，在结果适用时可跳过生成。Claude 文档明确前缀缓存不改变输出生成，且缓存存在组织/workspace 隔离；跨连接切换不能假设缓存共享。[Claude 前缀缓存](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)

当前 capability 的内容缓存用于减少能力定义读取，但已有固化复用还可以跳过规划模型，不能把项目概括成“没有免模型调用路径”。结果缓存尚未实现；若后续加入，应约束用户/权限、文件或世界状态版本、工具合同、模型配置和有效期，不能仅以用户目标语义相似跳过新的实际动作。查到的 Redis 官方 73% 数字描述高重复负载的推理成本下降，不能直接写成本项目调用量下降 73%。[Redis 对测量范围的说明](https://redis.io/blog/context-window-ai/)

减少不必要模型轮次有价值：已知工具、参数及依赖时可直接提交 TOOL DAG，未知且依赖实际返回的部分仍需后续规划。分叉/绑定/汇合本身都是程序操作，不自动发生模型调用；只有进入规划决策才调模型。应测量整条任务关键路径和完成质量，再决定动态路由、减少 TASK 包装或缓存哪类结果，尚无本项目实测证明其中一项一定比并发收益更大。

## 2026-11-12 按任务能力画像选型的方向及数据采集

用户提出以后按任务标签和模型历史能力选型，标签模块另行实现；并要求初次获取模型时保存模型对应的任务。循环已接入任务关联、调用开始和正常返回事件，失败事件补同一调用身份和规划耗时。目标、参数、允许工具、模型连接引用及分支/任务/轮次身份均按事实发送给独立记录模块，不在循环维护画像表或自动打标签。

每次具体任务取得绑定时即记录，后续轮次各有新 callId；已有绑定保持不变，纯工具路径不伪造模型样本。事件与实际效果/验收还需外部关联，模型正常返回不是任务成功。分叉已接入逐支任务描述和外部标签画像排序。未装配画像提供方时按配置顺序分配，根模型继续显式指定。后续适配器交接及模型/账号元数据要求见[27 第 9 节](27-模型适配器开发文档.md)，事件合同见[28](../records/28-执行记录与恢复端口开发文档.md)。
